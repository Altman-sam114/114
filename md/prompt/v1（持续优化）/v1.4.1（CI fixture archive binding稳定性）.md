# v1.4.1 CI fixture archive binding 稳定性

## 1. 版本号与分配依据

- 版本号：`v1.4.1`。
- 分配依据：v1.4 已完成产品实现和 archive binding 主逻辑，最新 `origin/main` 提交为 `5067079755039c12423c96870c24c560918d8ad2`；本轮是 v1.4 的补丁轮次，只修复云端 CI fixture 的生命周期、目录快照和 archive 绑定，不增加产品功能。
- 当前失败证据：GitHub Actions run `31294009115`（attempt 以精确 run API 为准）静态检查、macOS build 和 iOS build 已通过，只有 Project verification 失败；该 run 及 artifact 不能作为通过证据。
- 版本目标：在不改变 v1.4 验证合同和结果包结构的前提下，让完整第四模式恢复到 `131 PASS / 0 FAIL`。本轮不新增 PASS 项。
- 角色边界：Agent A 只提供本提示词；Agent B 只做最小 CI fixture 修复、提交并直接 push `main`；Agent C 只通过 `gh` 获取最新 `origin/main` 对应 run/artifact 并复判。

## 2. 背景

v1.4 的 `scripts/validate_ci_artifact.rb` 已把 archive integrity 和“原始 ZIP -> validator 自建临时解包目录 -> 调用方目录”的逐路径 type/size/SHA-256 binding 设为严格信任边界。该 validator 当前语义不能被放宽。

最新云端 artifact 的 `verify_project.log` 明确显示：run-metadata 正向 fixture validator 失败，首个失败为 `archive extracted directory binding`，详情为不同的 `verify_project.log`；随后出现 `index required local metadata` 和 `verify_project existing category reuse contracts` 失败。两次 validator 调用前的诊断状态均显示：

- `verify_project.log` 为 2356 bytes，SHA-256 为 `ffb615...`；
- `ci-artifact-index.json` 为 3545 bytes；
- `Existing category reuse contracts verified.` marker 在当前 fixture 中存在。

这说明当前失败不是 Swift 产品逻辑、Mac/iOS 编译或 validator 安全合同失败，而是 `scripts/verify_project.sh` 在多个 fixture 阶段之间复用 archive、目录和 index 元数据时没有稳定地保持同一份内容快照。尤其要检查：

1. artifact metadata 正向校验后，run-metadata 正向阶段重新生成 archive，但共享的 `artifact_fixture`、`artifact_archive_fixture`、archive size/digest 与 metadata 文件是否仍然一一对应；
2. archive 生成时 `verify_project.log` 和 `ci-artifact-index.json` 是否已经最终写入并稳定；
3. 任何改写 marker 或 index 的 archive-backed 负向 fixture 是否仍复用未改写目录的 archive；
4. index 的 `byteCount`、目录 `fileCount`/`recursiveByteCount` 和 totals 是否在 archive 创建前完成最后一次本地元数据复算。

## 3. 本轮目标

### 3.1 正向 run-metadata fixture 稳定

1. run-metadata 正向 validator 的第一个位置参数目录、`--archive` ZIP、`--archive-size`、`--archive-digest` 和 `--artifact-metadata` 必须来自同一个已经冻结的 fixture 内容快照。
2. archive 必须在 `verify_project.log`、`ci-artifact-index.json`、快照目录和所有 required entry 最终写入后生成；生成 archive 后不得再修改被绑定目录中的任何文件。
3. 不得只重新绑定 size/digest 字段而继续把 archive 与另一个目录传给 validator。禁止通过删除 binding 检查、跳过 binding 或把当前目录改成“自证”来掩盖错配。
4. 如果采用单独的 run-metadata fixture 目录，必须从完整、稳定的 baseline 复制出该目录，再从这份目录生成 ZIP，并把同一目录传给 run-metadata 正向调用；不能只替换 ZIP 路径而保留旧的 artifact fixture。
5. artifact metadata JSON 和 run metadata JSON 必须继续放在 fixture 根目录之外的全新临时路径中；它们的 API size/digest 与 workflow identity 必须重新绑定当前 ZIP，但不能被放进 ZIP 或让包内字段自证。

### 3.2 index 和既有分类 marker 保持独立

1. 正向 fixture 必须继续包含 `Existing category reuse contracts verified.` 以及所有既有 marker；正向 run-metadata 调用必须得到 `PASS verify_project existing category reuse contracts` 和 `PASS index required local metadata`。
2. 对每个改写 `verify_project.log` 或 `ci-artifact-index.json` 的 archive-backed 负向 fixture（至少 existing category reuse、existing category usage、existing category search、schedule-to-timer handoff、CI workflow run API metadata/provenance marker fixtures），要么：
   - 从该负向 fixture 的最终目录重新生成匹配 ZIP，并重新计算该 fixture 对应的 archive size/digest 和 artifact metadata；要么
   - 改为不带 archive 的目录-only 调用，但只能在不削弱该负向 fixture 原本要证明的合同时采用。
3. 每个“只移除一个 marker”的负向 fixture必须仍只得到目标 `FAIL verify_project ...`；archive 三项、binding、artifact metadata 八项、run metadata 14 项、index required local metadata 和其他 marker 都必须保持 PASS。
4. 不得把 marker 负向 fixture 的目录改回 baseline，也不得把目标 marker 断言删除、合并或改成宽松 substring 以规避失败。
5. 保留 v1.4 的等长普通文件错配 fixture：原始 ZIP、size/digest、三项 archive integrity 必须 PASS，且只有 `FAIL artifact archive extracted directory binding`；不能因为本轮做了 fixture helper 而把这个有意错配重新绑定成 PASS。

### 3.3 保留所有现有安全边界

- traversal、重复规范化路径、file/directory prefix conflict、symlink/特殊文件 ZIP 的拒绝路径保持不变。
- directory-only、archive-only、archive + artifact metadata、archive + artifact metadata + run metadata 四种模式的参数依赖和输出保持不变。
- `scripts/validate_ci_artifact.rb` 的 ZIP 解析、资源上限、非 symlink/hard link 检查、逐路径 type/size/SHA-256 比较、14 项 run metadata 和 8 项 artifact metadata 语义保持不变。
- 结果包 manifest、index allowlist、run context、JUnit、failure summary、artifact 名称和 workflow 不变。

## 5. 当前架构与关键文件依据

### 5.1 Fixture 生成边界

- `scripts/verify_project.sh` 在约 1904 行创建小型 artifact fixture，在约 2149 行补充 v1.4 startable marker 并复算 index。
- 约 2222 行创建第一份 archive fixture并验证 archive integrity/binding；约 2392 行创建 artifacts API fixture。
- 约 2450 行创建 run-metadata archive 并重绑 archive size/digest；约 2481 行创建 run API fixture；约 2560 行执行完整第四模式正向调用。
- 约 3709 行之后存在多个 archive-backed marker 缺失 fixture；它们修改 copied directory 后仍必须与自己使用的 archive 和 index metadata 同源。
- `report_artifact_fixture_state` 的诊断只读输出 bytes/SHA/marker 状态，不能修改 fixture，也不能替代 validator 结果。

### 5.2 Validator 信任边界

- `scripts/validate_ci_artifact.rb` 的 `validate_archive_extracted_directory_binding` 会从 ZIP 自建全新临时目录，再与第一个位置参数目录逐路径比较；它发现 `different verify_project.log` 是预期的 fail-closed 行为。

- validator 不应读取或写入 `verify_project.sh` 的临时 fixture；失败证据必须由调用方保留。

## 11. 风险与禁止项

- 最大风险是 strict archive binding 发现了真实 fixture 生命周期错误后，被通过放宽 validator、移除 binding 断言或重新使用旧 archive 掩盖；这些做法禁止。
- archive 创建后再写 log/index 会产生确定性 `different verify_project.log` 或 `index required local metadata`；必须把 archive 创建放在最终 index 稳定之后。
- 负向 marker fixture 若修改目录却复用 baseline archive，会把目标 FAIL 污染成 binding FAIL；每个 archive-backed变体必须独立绑定。
- 共享变量在 run-metadata 阶段重赋值可能让后续 fixture 组合使用错误的目录、ZIP 或 metadata；优先使用显式局部变量/helper，调用方不得隐式依赖最后一次赋值。
- 不得将 run-api JSON 或 artifacts API JSON 放入 artifact ZIP；包外 size/digest/run 状态/授权来源不能由包内字段自证。
- 不得删除或覆盖历史 `/private/tmp/chronofocus-c-review-*` 证据、当前失败 artifact、用户未跟踪文件或任何不明改动；默认不删除。
- 不得在本机运行测试、验证器、构建、模拟器或浏览器；不得用本地输出宣称通过。
- 保持模型 `grok-4.5 high`，不开 fast；Agent B/C 不得自行切换模型或绕过本轮角色边界。
