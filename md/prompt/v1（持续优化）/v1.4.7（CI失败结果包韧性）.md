# v1.4.7：CI 失败结果包韧性

## 版本与分配依据

- 版本：v1.4.7。
- 分配依据：v1.4.6 已完成 macOS 日历范围列表展开、分类上下文和云端五张快照验收；下一轮继续总目标中的 CI 证据强度优化，聚焦失败路径，不改产品 UI。
- 当前基线：`main` 与 `origin/main` 当前均为 `32d3fdcd0a0990c95b4b189c9694603064628c0f`。v1.4.6 实现 commit `53553007f9690e3c61495e4c1f7164d32bb9bc67` 对应的 GitHub Actions run `32629414670`、artifact `9490637377` 已由 Agent C 复判为 `132 PASS / 0 FAIL`；HEAD 之后仍必须重新查询最新 `origin/main`，不能复用旧证据作为本轮结论。
- 实施前必须再次执行 `git fetch origin`、`git switch main`、`git pull --ff-only origin main`，确认 HEAD、分支和工作区归属；用户未跟踪的 `md/1.md` 与 `md/通用云端迭代升级提示词.md` 不得修改、覆盖、加入提交或删除。

## 背景

当前 `.github/workflows/ci-results.yml` 只有 `Static checks`、`Project verification`、`Build ChronoFocusMac` 和 `Build ChronoFocus iOS` 四个带 id、`continue-on-error` 的后续阶段。`Checkout`、`Prepare result metadata`、`Select Xcode` 没有独立的 outcome 接线；元数据准备还负责创建 `ci-results`、写入 `GITHUB_ENV` 和 `ci-run-context.txt`。如果 checkout、工作目录初始化、环境准备或 Xcode 选择在这些早期步骤失败，后面的 manifest 生成可能读不到 `ARTIFACT_NAME` 或结果目录，最终的 `if: always()` 上传步骤仍可能因前置结果生成失败而没有可识别的 artifact。

当前工作流的正常路径是：创建 `ci-results` -> 运行静态检查/项目验证/两端 generic build -> inline Python 写入 `ci-artifact-manifest.json`、`ci-artifact-index.json`、`junit.xml`、`ci-stage-outcomes.json` 和唯一的 `ci-failure-summary.md` -> `actions/upload-artifact@v6` -> `Final CI status` 将摘要 tee 到 stdout 和 Step Summary 后按七阶段 outcome 退出。当前成功 validator 固定七个 stage outcome、JUnit 四个 testcase、精确 artifact 路径、`ci-run-context.txt` 五个键、manifest/index 身份字段和五张 Mac 正式 PNG；`scripts/verify_project.sh` 还会在云端编译 Mac core、渲染快照、执行源码合同和大量临时 negative fixture。

本轮必须让早期或后续任一阶段失败时仍能生成一个不伪装成功、身份可追溯、未加密、能由 Agent C 下载并复判的失败结果包；同时成功路径的严格验收和 Mac 正式快照清单保持不变。

## 目标

1. 增强 `.github/workflows/ci-results.yml`，使 `Checkout`、`Prepare result metadata`、`Select Xcode` 以及四个后续阶段失败时，始终尽力创建并上传一个可识别的未加密 CI artifact；artifact 上传必须发生在 `Final CI status` 之前，上传成功后 job 仍以失败状态结束。
2. 为早期阶段建立独立、可结构化复判的 outcome 和失败摘要，不让缺少 checkout 源码、Xcode、日志、`.xcresult` 或快照把“失败 artifact”误判成“成功 artifact”，也不让 fallback 元数据掩盖真实失败。
3. 用 `scripts/verify_project.sh` 对 workflow 的具体步骤边界、`always()`/`continue-on-error`、兜底身份、上传顺序、无加密和最终失败传播建立精确源码合同；用 `scripts/validate_ci_artifact.rb` 增加显式 opt-in 的失败结果包模式和 `--expected-event` 来源约束，且默认成功模式继续严格拒绝不完整包。
4. 增加一个小型正向 failure fixture 和仅目标失败的 negative fixture：正向 fixture 应能证明“没有 checkout 产物、xcresult 或正式快照时仍可识别失败包”；每个负例只破坏一个字段、marker、阶段连接或 allowlist 项，并只产生对应的 `FAIL`。
5. 保留当前 Mac 五张正式快照清单和安全验收：`mini-timer.png`、`detail-timer.png`、`detail-schedule.png`、`detail-analytics.png`、`detail-settings.png`，不加入临时失败图、placeholder PNG 或额外 artifact 文件。

## 非目标

- 不把失败路径简单改成全部成功、吞掉 `Final CI status`、只上传文字汇报、把 artifact 放进加密 ZIP、或用旧 artifact/本地输出代替最新云端证据。
- 不增加第三方依赖，不引入 PR/develop/`smalldata_test`/`codeb/...` 流程，不迁移到其他 GitHub 账号。

## 当前架构依据

- `.github/workflows/ci-results.yml` 是唯一默认云端入口，运行在 `macos-latest` 的单 job `ci-results`；当前 action 版本为 `actions/checkout@v5` 和 `actions/upload-artifact@v6`，不得降级或重复声明。
- 结果目录根为 `ci-results`。inline Python 负责 manifest、index、JUnit、failure summary 和错误摘录；上传 action 只上传该目录，不能另开一份不受 validator 约束的旁路包。
- 现有 `ci-run-context.txt` 由 `artifactName`、`branch`、`commitSha`、`runId`、`runAttempt` 五个键组成，validator 要求精确键集；不要把早期 outcome 塞入该文件。若需要新增结构化数据，使用独立的 `ci-stage-outcomes.json`（或同等独立文件），并在 workflow、index、manifest、validator、fixture 中同源接线。
- 现有成功 validator 的 `EXPECTED_INDEX_ENTRIES`、`EXPECTED_ARTIFACT_ROOT_ENTRIES`、`EXPECTED_MAC_SNAPSHOT_ENTRIES`、manifest 路径、JUnit 四 testcase 和 `EXPECTED_SNAPSHOTS` 是相互绑定的合同。任何新增 failure-only 文件必须明确列入 allowlist；任何失败模式可缺失的路径必须由 index 的 `required`/profile 语义准确表达，不能靠忽略额外文件放行。
- Agent C 的验证有目录-only、archive 三参数、archive 加 artifact metadata、archive 加 artifact metadata 加 run metadata 四种模式。正式验收只接受最后一种；原始 run/artifacts API JSON 是包外信任输入，ZIP 的 API size/digest 不能由包内 manifest 自证。

## 实现步骤

### 1. 同步、审阅和变更边界

1. 从最新 `origin/main` 开始，只检查本轮相关 diff；不要覆盖当前工作区的用户未跟踪文件。
2. 阅读本提示词、`AGENTS.md`、`update_log.md`、`md/flow/flow.md`、`md/flow/flowchart.md`、`md/test/test.md`、`README.md`、`md/prompt/README.md`，以及当前 workflow、两个脚本和最近 v1.4.6 记录。
3. 修改范围限定为 `.github/workflows/ci-results.yml`、`scripts/verify_project.sh`、`scripts/validate_ci_artifact.rb` 及受影响的 `README.md`、`update_log.md`、`md/test/test.md`、`md/flow/*`、`md/prompt/README.md`。不得修改 Swift 文件或正式快照资源。

### 2. Workflow 失败传播和兜底结果包

1. 给 `Checkout`、`Prepare result metadata`、`Select Xcode` 分配稳定 id，并让它们的 outcome 进入统一 stage 表；早期步骤失败后，后续准备、日志收集、manifest、上传和最终状态步骤都必须用精确的 `if: always()`/`continue-on-error: true` 组合继续到可执行的最远位置。不要只在末尾写一个宽泛 `always()` 字符串来满足合同。
2. 元数据准备必须尽量只依赖 GitHub runner 上下文和 shell/Python 标准库，不依赖已 checkout 的项目文件。即使 checkout 没有完成，也要创建结果目录、写入身份 context、确定 branch/commit/run/attempt 和 artifact 名称，并写出一个非空的阶段状态/失败说明。
3. 设计确定性的 fallback artifact name。正常路径继续使用当前 `chronofocus-ci-v0.10-<branch-slug>-<short-sha>-run<id>-attempt<attempt>` 格式；若准备步骤未能写入短 SHA 环境变量，fallback 也必须包含 process version、branch、可追溯的完整 SHA 或等价唯一标识、run id 和 attempt，并在 manifest、index、stage file、context、artifact API 期望名之间完全一致。不要让 upload step 依赖一个可能未定义的 `GITHUB_ENV` 变量。
4. 建议新增 `ci-results/ci-stage-outcomes.json` 作为独立结构化合同，至少包含版本、artifactName、branch、commitSha、runId、runAttempt、createdAt、`overallOutcome`、失败模式/失败阶段和以下七个稳定阶段：`checkout`、`prepareMetadata`、`selectXcode`、`staticChecks`、`projectVerification`、`macBuild`、`iosBuild`。每个 outcome 只能是明确的 `success`、`failure`、`skipped`、`cancelled` 或 `unknown` 之一；`overallOutcome` 不是 success 时必须列出至少一个 failure/cancelled/unknown 的原因，不能把 skipped 当成成功。
5. manifest 和 failure summary 必须同时记录早期阶段结果、失败阶段、fallback 是否使用、日志/产物是否未生成和包的整体结果。成功 summary 继续保留 `All CI stages passed.`；失败 summary 不得出现该句，必须列出 first failed stage、所有非 success 阶段及可用的错误摘录。不能把 Checkout 失败写成普通项目验证失败而丢失根因。
6. 结果生成步骤必须是幂等、可重入且有最小 fallback：无论前置阶段是否创建了日志、`.xcresult` 或快照，至少生成非空的 manifest、index、summary、JUnit、run context 和 stage outcome 文件。无法生成的阶段产物要以可验证的 optional/missing 状态进入 index，而不是伪造空的成功产物；任何真实存在的文件仍必须逐项纳入 allowlist 和 byte metadata。
7. `actions/upload-artifact@v6` 必须保持唯一、`if: always()`、上传 `ci-results` 根目录，并在 `Final CI status` 之前执行；保留 `if-no-files-found` 的明确行为。不得使用密码、`encrypt`、`gpg`、`openssl`、`zip -P`、手工加密压缩或把原始 API JSON 放进 artifact。GitHub upload-artifact 产生的普通未加密 ZIP 仍由 Agent C 用原始 API size/digest、ZIP 结构和加密标志复判。
8. `Final CI status` 必须在 artifact 上传之后运行，继续把唯一 failure summary 用 `tee` 输出到 stdout 和 Step Summary，然后根据七个阶段的真实 outcome 返回非零。artifact 上传成功不能把 workflow conclusion 变成 success；失败 run 仍需能被 `gh api` 查询和下载。
9. 为了云端实际覆盖失败路径，可增加仅 `workflow_dispatch` 可用、默认 `none` 且不影响 push 的受控 failure injection（至少覆盖 checkout 边界、metadata preparation、Xcode selection 和一个后续阶段）。注入必须写入 stage outcome 并走同一 package/upload/final-status 路径；不能在默认 push 中触发，也不能为了测试改动源文件或正式快照。

### 3. `verify_project.sh` 精确 workflow 合同

1. 扩展现有 `verify_ci_failure_summary_output`，并新增一个职责单一的 workflow resilience helper。按 step heading/step 区间或结构化解析逐项验证：唯一 checkout/upload、稳定 id、早期步骤的 `if: always()`/`continue-on-error`、四个后续阶段的继续执行、manifest/index/stage writer、upload-before-final 顺序、final failure condition、fallback artifact name、无加密字段和唯一 `ci-results` upload path。禁止只用全文件 `include?`、无边界 `grep` 或无关字符串计数来证明接线。
2. 精确检查 workflow 的 stage 名称与 `steps.<id>.outcome` 映射，确保 `skipped`/`cancelled`/`unknown` 不会被当作成功；检查正常 artifact name 公式和 fallback 公式都能被 manifest/index/context 复用；检查 failure summary 只有一个 writer，避免两个来源互相覆盖。
3. 保留现有 action version、iOS generic build、Mac core/snapshot 路径、Final CI status 的 tee 合同和所有既有 marker。新增一个清晰的正向日志 marker，例如 `CI failure artifact resilience contracts verified.`，并让 `validate_ci_artifact.rb` 对应输出一个独立 PASS。
4. 为每个独立新合同准备临时 negative fixture：例如只移除 checkout 的 `always()`、只删掉 prepare fallback、只改 stage outcome 映射、只把 upload 放到 final 之后、只加入一个加密/密码字段、只删除 stage marker。每个 fixture 必须从新 `mktemp` 副本开始，运行对应 helper 后确认目标错误出现、目标 PASS 不出现且 `^FAIL ` 计数为 1；不得依赖另一个失败来“顺带”证明合同。
5. 继续用小型成功 fixture 建立失败包 fixture 的正向路径。失败 fixture 应只包含身份文件、stage outcome、summary、JUnit、index 和必要日志，不包含五张快照或 `.xcresult`，并能在 failure mode 下通过；其 index、目录 allowlist、byte totals 和 archive 必须同源稳定。负例只破坏一个字段/文件/marker 后再重算必要 index，避免 fixture 因无关的旧 totals 产生多项 FAIL。

### 4. `validate_ci_artifact.rb` 的双模式合同

1. 增加明确的 opt-in failure mode（例如 `--failure-mode`，名称可等价但必须显式），默认仍是现有 success mode。failure mode 必须强制要求完整 archive 三参数、`--artifact-metadata` 和 `--run-metadata`，不能让目录-only 或缺少包外来源的输入伪装成失败验收。
2. success mode 继续要求当前成功 artifact 的四个 JUnit testcase、`failures=0`、`errors=0`、所有 success outcome、所有 required entries、两端 `.xcresult`、Mac snapshot manifest 精确五张和五张 PNG byteCount 一致；不要为了让失败包通过而放宽这些检查。
3. failure mode 仍必须检查固定 CI process version、workflow name/path、branch、commit、run id、attempt、artifactName、run context 精确五键、manifest/index 身份、summary 身份、artifact API 的唯一 id/name/size/digest/expired、run API 的 id/attempt/SHA/branch/name/path/status/conclusion/repository/event/actor/triggering actor/head repository，以及原始 ZIP 的 size、SHA-256、结构、目录绑定和未加密 entry。默认失败验收只接受授权 `push` run；受控 `workflow_dispatch` 失败只能在命令显式传入 `--expected-event workflow_dispatch --failure-mode` 时验收，不能伪装成 push；两种来源都必须是 `status=completed`、`conclusion=failure`，success mode 仍只接受 `conclusion=success` 和默认 `push`。
4. failure mode 必须要求 manifest/stage file 的 `overallOutcome=failure`，至少一个真实失败 stage，失败阶段名在固定七项集合内，summary 明确列出失败阶段和不可用产物；不允许只改 summary 文案而让 manifest/index/stage 三方互相矛盾。应区分 `failure`、`cancelled`、`skipped`、`unknown`，并按 profile 规则检查 `required` 与 optional/missing entry。
5. failure mode 的 artifact root、`project-reports` 和 Mac snapshot 目录仍必须使用精确 allowlist：允许缺少尚未运行产生的日志/`.xcresult`/快照，但禁止任何额外文件、额外 PNG、symlink、特殊文件、路径穿越、重复 ZIP entry、前缀冲突或加密 ZIP entry。若已经生成快照，只能是现有五个文件名；不得把失败截图或临时 overflow 图塞进正式包。
6. 为新增检查提供独立、可读的 PASS 名称，例如 `PASS failure artifact stage outcomes`、`PASS failure artifact summary`、`PASS failure artifact required metadata`、`PASS failure artifact optional entries`，并在 `verify_project.sh` 的正向小型 failure fixture 上执行完整 archive + artifact metadata + run metadata 第四模式。不要复用一个宽泛 PASS 来掩盖多个独立合同。
7. 为每个 failure-only 检查加入一个只移除/篡改单项目标的 negative fixture，例如删 stage outcome、改 overall outcome、删 failure summary 身份、把 run conclusion 改成 success、加入额外文件或把 stage outcome 改成未知值。每个负例都要确认目标 `FAIL`、目标 `PASS` 缺失且没有第二个 `FAIL`；保留已有 success fixture 的所有 PASS。
8. 保持已有四种 CLI 参数矩阵、`--artifact-metadata`/`--run-metadata` 的前置约束和 archive directory binding 安全边界。`--expected-event` 默认是 `push`，只有 failure mode 才允许显式选择 `workflow_dispatch`；缺少所需前置参数必须明确报参数错误，不能通过自动从包内 manifest 推导 API size、digest、attempt、event 或 conclusion。

## 云端测试要求

- Agent B 只做静态阅读和 diff 审阅，不在本机运行 `bash scripts/verify_project.sh`、`ruby scripts/validate_ci_artifact.rb`、项目测试、任何 `swiftc`/Xcode/`xcodebuild`、`simctl` 或 Simulator；不使用浏览器。所有测试、构建、validator 和 failure fixture 由 push 后的 GitHub Actions 执行。
- 正常 push 云端必须运行现有 Static checks、Project verification、Mac core/snapshot、`ChronoFocusMac` build、`ChronoFocus` iOS generic build、manifest/index/JUnit/failure summary、artifact upload 和 Final CI status。成功 run 应保持 `JUnit 4 tests / 0 failures / 0 errors`、既有 success PASS 全部存在、正式五张 Mac 快照精确存在，新增 success/failure-resilience PASS 只反映真实合同。
- 至少一次云端 `workflow_dispatch` 受控失败应覆盖早期阶段，确认 run conclusion 是 failure 但 artifact upload 成功；该 run 只能用 `--expected-event workflow_dispatch --failure-mode` 复判，不能改写事件或冒充 push。若实现了多个 injection，应分别覆盖 checkout boundary、prepare metadata、select Xcode，并至少覆盖一个后续阶段。失败 run 不得被 Agent B 文字汇报替代，必须通过原始 artifact 复判。
- 失败路径若受 GitHub runner 或 action 本身不可控因素影响，保留原始失败证据并说明阻塞；不得把本地模拟输出写进 update log 充当云端证据。工作流默认 push 不能因为 injection 配置而失败。

## 风险和禁止项

- GitHub Actions 中 `if: always()`、`continue-on-error`、`steps.<id>.outcome`、`GITHUB_ENV` 和 action expression 的求值时机容易造成“步骤看似继续、artifact name 未定义”或“job 被错误标记成功”；必须用 job 级 fallback、独立 stage 文件和云端受控失败验证，不要凭本地 YAML 阅读猜测。
- checkout 失败时仓库脚本可能不存在，manifest/fallback writer 不能调用 checkout 后的脚本；包装逻辑必须内联且只依赖 runner 上下文。若 runner 无法写入任何结果目录，必须让上传失败原因可见，不能伪造成功包。
- 不要用 `always()` 让真正的错误被吞掉；`Final CI status` 必须在上传后明确退出非零。上传成功是证据可获得性，不是构建成功。
- 不得通过放宽 `EXPECTED_INDEX_ENTRIES`、删除 snapshot 检查、忽略额外文件、从包内读取 API size/digest、接受错误 actor/repository 或把 failure conclusion 当 success 来提高通过率。
- 不得新增正式快照、覆盖历史 artifact、清理旧 Agent C 证据、修改用户未跟踪文件、运行浏览器或任何本机项目测试/构建/validator。
