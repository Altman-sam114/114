# v1.0：已有分类复用与 Run API 复判

## 1. 版本号与分配依据

- 版本号：`v1.0`。
- 版本分配依据：当前最新闭环实现版本为 v0.99；本轮同时补齐跨 iOS/macOS 的已有分类复用主流程，并把 Agent C 的外部证据链从 artifacts API 延伸到精确 workflow run API，因此在 v0.99 后进入首个大版本里程碑，版本定为 v1.0。
- 固定提交信息：`v1.0: 复用已有分类并复判Run API`。
- 协作分支固定为 `main`。实现、提交、push、GitHub Actions 和 Agent C 验收均只针对最新 `origin/main`。
- 本轮提示词路径固定为：`md/prompt/v1（持续优化）/v1.0（已有分类复用与Run API复判）.md`。

## 2. 背景

### 2.1 已有分类无法在录入表单中直接复用

当前 `FocusStore.taskCategories` 已把固定预设、任务分类和历史会话分类合并为完整分类列表。iOS 计时、iOS 日程、Mac 计时和 Mac 日程的筛选器都会使用这份列表，因此用户能在筛选器中看到自定义分类。

但两个分类录入入口仍只提供自由文本和 5 个固定预设：

- iOS `ScheduleView.swift` 中的 `TaskEditorView`，同时服务新增和编辑待办；
- macOS `MacScheduleDetailView.swift` 中的快速新增表单。

用户要复用“客户 A”“研究”“健身”等已有自定义分类时，必须手动输入完全一致的名称。大小写、全半角、前后空白或轻微拼写差异会让数据继续分裂成多个近似分类，之后计时筛选、日程筛选和统计分类投入也会被拆开。

本轮保留自由文本和 5 个固定预设，在两端增加去重后的“已有分类”横向选择，让分类录入与现有筛选来源一致。

### 2.2 Run API 尚未进入 validator 外部证据链

v0.99 已让 `scripts/validate_ci_artifact.rb` 接收 `--artifact-metadata artifacts-api.json`，结构化核对唯一 artifact 的 id、name、size、digest、expired 和 `workflow_run.id/head_sha/head_branch`。Artifacts API 的 `workflow_run` 不包含 `run_attempt`，也不能证明 workflow 的 name/path、最终 status/conclusion 或仓库身份；这些仍由 Agent C 手工核对。

GitHub 精确 run endpoint：

```text
GET /repos/Altman-sam114/114/actions/runs/<run_id>
```

会返回本轮需要的 `id`、`run_attempt`、`head_sha`、`head_branch`、`name`、`path`、`status`、`conclusion` 和 `repository.full_name`。本轮新增可选 `--run-metadata JSON`，要求它只在 v0.99 完整 archive + artifact metadata 模式之上启用，并由 validator 无网络地结构化复判。

Run API JSON 与 artifacts API JSON 一样，只是 Agent C 在 artifact 外保存的原始外部证据，禁止加入 GitHub Actions artifact 或扩大上传内容。

## 3. 本轮目标

### 3.1 UI 目标

1. iOS `TaskEditorView` 的新增和编辑模式继续保留分类自由文本输入及 5 个固定预设。
2. macOS `MacScheduleDetailView` 快速新增继续保留分类自由文本输入及相同 5 个固定预设。
3. 两端在存在非预设历史分类时显示“已有分类”横向选择区；数据只来自 `store.taskCategories`。
4. “已有分类”必须按统一规范化比较键排除预设、去重，并保持与当前 `store.taskCategories` / `store.tasks` 顺序一致的稳定顺序。
5. 点击已有分类只改变当前表单草稿，不直接写 `FocusStore`；分类草稿切换到所选显示名称，并优先复用该分类现有任务的代表 `accentHex`。
6. 当前已有分类项显示 selected 状态；再次点击当前项不得清空分类。
7. 正确覆盖 initial category、编辑现有 task、只存在于 session 的分类、当前分类不在列表中，以及大小写/空白近似名称。
8. 两端支持动态字体、VoiceOver、Voice Control 和非颜色 selected 指示；iOS 交互项至少 44pt。

### 3.2 CI 目标

1. `scripts/validate_ci_artifact.rb` 新增可选文件参数 `--run-metadata JSON`。
2. `--run-metadata` 只能在完整 archive 三参数和 `--artifact-metadata` 同时存在时提供；缺少任何前置参数必须拒绝，不得降级。
3. Run metadata 文件采用与 artifact metadata 相同的安全限制：存在、非空、普通文件、拒绝 symlink、最大 `1_048_576` bytes，并使用 `JSON.parse` 结构化解析。
4. 严格复判 run JSON 的 `id/run_attempt/head_sha/head_branch/name/path/status/conclusion/repository.full_name`。
5. 固定预期 workflow name 为 `ChronoFocus CI Results`，workflow path 为 `.github/workflows/ci-results.yml`，repository 为 `Altman-sam114/114`。
6. 保留目录-only、archive-only、archive + artifact metadata 三种既有兼容模式；新增第四种 archive + artifact metadata + run metadata 完整模式。
7. 为每项 run metadata 证据输出独立、可定位的 PASS/FAIL，增加项目 marker、validator PASS、成功 fixture、安全 fixture、参数矩阵 fixture、逐字段负向 fixture和 marker 缺失 fixture。
8. 每个 run metadata 字段负向 fixture 必须明确证明三个 archive PASS 和八个 artifact metadata PASS 仍然通过，避免用前置失败掩盖目标字段错误。
9. Agent C 从精确 run endpoint 原样保存 `run-api.json.part`，成功后无覆盖原子改名为 `run-api.json`，并与 artifacts API JSON、原始 ZIP、解包目录一起传给 validator。

## 5. 当前架构依据与边界

### 5.1 分类数据边界

- `FocusStore.taskCategories` 是本轮已有分类的唯一来源。它当前依次组合固定预设、`tasks` 数组中的分类和 `sessions` 数组中的分类，再按清洗后的精确字符串首次出现去重。
- `FocusStore.addTask` 与 `FocusStore.updateTask` 仍是实际保存入口；本轮分类按钮只修改 View 的 `category` / `accentHex` 草稿绑定。
- iOS `TaskEditorView` 已持有 `@EnvironmentObject store`、`category` 和 `accentHex`，新增/编辑均复用该 View。
- macOS `MacScheduleDetailView` 已持有同样的 store、category 和 accentHex 草稿，快速新增继续调用既有 `addTask()`。
- `TaskCategoryPreset` 当前源码把完整预设集合命名为 `defaults`。本规格中题述的 `TaskCategoryPreset.all` 指这份完整 5 项预设集合；Agent B 不需要仅为命名而重命名 API。若确有必要增加 `all` 别名，必须保持 `defaults` 兼容且不得扩大重构。
- 平台 UI 可以各自实现薄的横向选择 View；不得为消除少量 SwiftUI 重复而引入跨 target UI 文件或条件编译共享 View。

### 5.2 分类规范化比较键

显示值、保存值和比较键必须分开处理：

1. 显示/选择值先使用 `trimmingCharacters(in: .whitespacesAndNewlines)` 清理前后空白；清理后为空时使用现有语义 `未分类`。
2. 比较键在清理值基础上执行大小写、变音符号和宽度不敏感 folding；使用固定 locale（建议 `Locale(identifier: "en_US_POSIX")`）保证稳定，不使用随设备变化的本地化排序作为身份判断。
3. 预设集合也用同一比较键生成 key set。“工作”和带前后空白的“ 工作 ”必须视为同一个预设；英文自定义分类的 `Client` / `client` 也只显示首次出现项。
4. 规范化只用于本轮 UI 的排除、去重和 selected 判断，不改写现有 `FocusStore.normalizedCategory` 的持久化语义，不批量迁移历史数据。
5. 点击一个已有分类时，写入该选项首次出现的清理后显示值；不得把 folding 后的 key 当成可见或保存名称。

可在两个平台文件中各自实现小型纯计算 helper，或在现有非持久化模型边界增加最小共享 helper；禁止新增 Codable 字段或平台 UI 抽象。若增加共享 helper，必须有云端 core test 覆盖且保持现有 API 兼容。

### 5.3 已有分类稳定顺序

“已有分类”选项必须按以下确定算法生成：

1. 顺序遍历 `store.taskCategories`，不得先放入无序 `Set` 后再直接输出。
2. 对每个字符串生成清理后显示值和规范化比较键。
3. 如果 key 属于完整预设 key set，排除。
4. 如果 key 已在本轮输出中出现，排除；首次出现的显示值获胜。
5. 其余项按首次出现顺序输出，不做字母、本地化、计数或颜色二次排序。

这一定义与现有 store 顺序契合：过滤掉开头的固定预设后，当前 `tasks` 数组中首次出现的自定义分类优先，随后才是仅存在于历史 `sessions` 的分类。任务数组当前以仓库实际顺序为准，不得在 View 中擅自按标题或日期重新排序分类。

### 5.4 代表色确定算法

点击已有分类时，必须按以下规则更新草稿：

1. 先把草稿 `category` 设置为该选项的清理后显示值。
2. 使用同一规范化比较键，从 `store.tasks` 当前数组顺序的开头查找首个分类 key 相同的任务。
3. 找到时，把草稿 `accentHex` 设置为该首个任务的 `accentHex`；这就是该分类本轮唯一的代表色算法。
4. 没有匹配任务时，说明分类可能只来自历史 session；此时保留当前草稿 `accentHex`，不得伪造颜色、从 session 推断颜色或强制回退绿色。
5. 固定预设按钮继续使用各自 `TaskCategoryPreset.accentHex`，行为不变。
6. 编辑现有 task 时，如果当前自定义分类被选中但用户未点击其他项，必须保留 task 自身原有 `accentHex`；不得因 View 出现而自动改色。
7. 点击已选中的已有分类可以保持 category/代表色不变，但不得切换为 nil、空字符串或 `未分类`。

### 5.5 Run metadata 信任边界

- `--commit`、`--run-id`、`--attempt` 继续必填，`--branch` 默认 `main`。
- `--archive`、`--archive-size`、`--archive-digest` 继续全有或全无。
- `--artifact-metadata` 继续要求完整 archive 三参数。
- `--run-metadata` 进一步要求完整 archive 三参数和 `--artifact-metadata` 同时存在。
- Run API JSON 是包外输入，不能由 manifest、artifact index、run context 或 ZIP 内字段自证。
- Validator 只证明传入原始文件、CLI 参数、ZIP 和解包内容相互一致；GitHub 账号、endpoint、HTTP 来源和“这是最新 run”仍由 Agent C 下载流程保证。
- 与 artifacts API 不同，精确 run API 直接包含 `run_attempt`；v1.0 完整模式必须把它与 `--attempt` 交叉核对。

### 6.6 `--run-metadata` 参数矩阵

在 `scripts/validate_ci_artifact.rb` 的现有结构化参数解析上增加 `--run-metadata PATH`，PATH 只表示原始 JSON 文件，不接受内联 JSON。

允许模式：

| Archive 三参数 | Artifact metadata | Run metadata | 结果 |
| --- | --- | --- | --- |
| 全无 | 无 | 无 | 保持目录-only 兼容 |
| 全有 | 无 | 无 | 保持 archive-only 兼容 |
| 全有 | 有 | 无 | 保持 v0.99 artifact metadata 模式兼容 |
| 全有 | 有 | 有 | v1.0 完整 run metadata 模式 |

必须拒绝：

- 任意部分 archive 参数；
- artifact metadata 脱离完整 archive 三参数；
- run metadata 脱离完整 archive 三参数；
- run metadata 在没有 artifact metadata 时提供，即使 archive 三参数完整；
- run metadata 只有 artifact metadata 但 archive 参数不完整；
- 空参数值或无法读取的路径。

参数错误必须清楚列出前置要求，不得静默忽略 `--run-metadata` 或退回较弱模式。既有三个模式的 PASS/FAIL、退出码和参数语义必须保持兼容。

### 6.7 Run metadata 文件安全

Run metadata 文件必须在 JSON 读取前验证：

- 路径存在；
- `lstat` 或等价检查确认是普通文件；
- 明确拒绝 symlink，即使 symlink 最终指向普通文件；
- 文件大小大于 0；
- 文件大小不超过 `1_048_576` bytes；
- 使用 UTF-8 和 `JSON.parse`；
- JSON 顶层必须是 object，不能是 array、scalar 或 null。

优先复用 v0.99 artifact metadata 的安全读取 helper，避免两套限制漂移；如重构 helper，必须保持八个 artifact metadata PASS、所有既有错误文案和 fixtures 兼容。禁止 `eval`、YAML、字段 grep、shell 字符串切片、网络请求或执行 JSON 内容。

未知 GitHub 扩展字段允许存在，不要求顶层精确键集；只严格验证本规格字段的存在、类型和值。

### 6.8 Run API 结构化字段复判

完整模式下必须验证：

1. `id`：JSON integer、正数，严格等于 `--run-id`。
2. `run_attempt`：JSON integer、正数，严格等于 `--attempt`。
3. `head_sha`：JSON string，严格等于 `--commit`；不得只比 short SHA。
4. `head_branch`：JSON string，严格等于 `--branch`，本轮应为 `main`。
5. `name`：JSON string，严格等于 `ChronoFocus CI Results`。
6. `path`：JSON string，严格等于 `.github/workflows/ci-results.yml`。
7. `status`：JSON string，严格等于 `completed`。
8. `conclusion`：JSON string，严格等于 `success`。
9. `repository`：必须为 object。
10. `repository.full_name`：JSON string，严格等于 `Altman-sam114/114`。

不得接受数字字符串、truthy/falsy 转换、大小写宽松匹配、路径后缀匹配、仓库短名或 null。`name/path/repository.full_name` 使用 validator 内明确常量，不增加可由调用者任意覆盖的参数。

同时交叉保证：

- run JSON `id` 与 CLI `--run-id`、artifact metadata `workflow_run.id`、manifest/index/run context run id 一致；
- run JSON `head_sha/head_branch` 与 CLI、artifact metadata workflow_run、manifest/index/run context 一致；
- run JSON `run_attempt` 与 CLI、artifact 名称中的 attempt、manifest/index/run context 一致；
- run JSON success 不能覆盖任何 archive、artifact metadata、manifest、build 或 marker 失败。

## 12. 风险与处理

- **大小写语义与持久化语义不同**：本轮只在选择 UI 中折叠近似名称，不迁移历史数据；首次出现显示值获胜，保存仍由现有 FocusStore 清理。
- **无序 Set 导致分类跳动**：Set 只可用于 membership；最终输出必须来自对 `store.taskCategories` 的顺序遍历。
- **编辑打开即改色**：代表色只在用户点击已有分类时应用，不能放在 `onAppear` 或普通 computed property setter 中。
- **session-only 分类没有颜色**：保持草稿当前 accentHex，禁止假装存在代表任务颜色。
- **Mac snapshot 与真实 UI 分叉**：两条渲染路径必须消费同一已有分类计算结果，静态控件只替换渲染，不复制业务规则。
- **Run API rerun 身份**：`run_attempt` 必须严格等于 CLI attempt，并继续与 artifact 名称和包内 runAttempt 交叉核对。
- **错误 run 仍可能字段自洽**：固定 workflow name/path/repository/status/conclusion，并由 Agent C 保证精确 endpoint 和最新 origin/main 来源。
- **安全 helper 重构回归 v0.99**：复用文件安全逻辑时必须保留所有 artifact metadata PASS、fixtures 和错误边界。
- **逐字段 fixture 提前退出**：完整字段负例必须继续执行 archive 和 artifact metadata 检查，不能因 run 字段先失败而丢失 11 项不受影响证据。
- **响应扩大**：读取前执行 1 MiB 上限；未知字段允许但不能绕过必要字段类型和值。

- 禁止回滚失败提交；失败只能在 `main` 追加修复 commit。

## 14. Commit、Push 与 Agent C 闭环

Agent B 完成实现与文档后：

1. 只读核对实际 diff、文件归属和当前分支，不运行任何检查。
2. 仅暂存 v1.0 相关文件，明确排除两份未跟踪用户文件和其他无关 diff。
3. 确认 `update_log.md` 已记录 v1.0 真实实现；云端证据未产生时写 pending，不伪造结果。
4. 使用固定提交信息：`v1.0: 复用已有分类并复判Run API`。
5. 确认当前分支为 `main`，push 目标为 `origin/main`，授权账号为 `Altman-sam114`。
6. 执行 `git push origin main` 触发 `.github/workflows/ci-results.yml`。
7. 记录真实完整 commit SHA、run id、run attempt、run status/conclusion、artifact id/name/API size/digest/expired 和 workflow run 身份。

Agent C 必须按第 7 节取得最新精确 run JSON、artifacts JSON 和原始 ZIP，执行完整 validator 调用。以下任一情况都必须判定不通过并退回 Agent B：

- GitHub Actions 任一阶段失败；
- Run JSON、artifacts JSON、ZIP 来源或身份不一致；
- UI marker、Run API marker、fixture、snapshot、Mac build、iOS build、manifest、JUnit、failure summary 或日志失败；
- Validator 有任何 FAIL，或缺少十个 run metadata、八个 artifact metadata、三个 archive PASS；
- 文档未同步或存在未说明风险。

失败后 Agent B 只能在 `main` 追加最小修复 commit 并重新 push，不回滚旧提交，不复用旧 run/artifact。

首次实现 run 通过后，必须把真实云端证据补入 `update_log.md`、`md/test/test.md` 和 `md/prompt/README.md` 等要求的文档。该证据记录 commit 会成为新的 `origin/main` HEAD，因此它本身必须再次触发 GitHub Actions，并由 Agent C 重新获取该新 commit 对应的 `run-api.json`、`artifacts-api.json` 和 ZIP，完成同样的完整复判。

只有最新 `origin/main` 最终证据提交自身满足以下条件，v1.0 才能宣布闭环：

- 精确 run API 为 completed/success；
- 最新 artifact 下载和来源核对通过；
- 十个 run metadata PASS、八个 artifact metadata PASS、三个 archive PASS、所有项目 marker 和 build 全 PASS；
- Validator 零 FAIL；
- 文档记录的 SHA/run/attempt/artifact 与最新外部证据一致。
