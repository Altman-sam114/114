## 背景

v1.2 已在 iOS `TaskEditorView` 和 macOS 快速新增区域为至少 6 个非预设已有分类提供名称搜索、结果计数、清除和无结果反馈，但日程待办列表与 iOS/macOS 计时队列的分类筛选栏仍直接渲染完整横向 chip。分类增多后，用户必须反复横向滚动，且 iOS 与 macOS 仍分别维护筛选 UI 和部分分类比较辅助方法。当前筛选排序入口是共享的 `TaskCategoryPreset.prioritizedFilterOptions`，分类匹配应继续通过 `FocusStore.categoryMatches`；代表色、任务数量、session-only 分类和持久化边界均已由 v1.4.8 定义，不应在本轮重新实现。

## 本轮目标

1. 让 iOS 日程筛选、iOS 计时筛选、macOS 日程任务列表筛选和 macOS 计时待办队列筛选在分类数量达到长列表阈值时显示瞬态搜索控件；搜索按分类名称子串过滤可见 option，提供结果数/总数、清除和无结果反馈。
2. 让四处筛选使用同一规范化 key、空查询语义、阈值、过滤顺序、选中状态、计数来源、VoiceOver/Voice Control 文案和清除行为；搜索不能改变 `selectedCategory`、任务草稿、代表色、`FocusStore` 或 UserDefaults。
3. 保留已有分类新增/编辑搜索的行为，并尽量复用同一共享搜索 helper；修正 macOS 本地重复的分类 folding/key 逻辑，使产品行为和静态快照使用同一派生结果。
4. 增加一个独立、边界明确的 `verify_project`/validator 云端合同，证明共享搜索规则和四处 UI 接线存在；负向 fixture 只破坏本轮合同，不放宽既有 artifact、双端构建或 v1.4.8 包阶段合同。

- 共享模型/分类元数据：`ChronoFocus/Models/AppModels.swift`。`TaskCategoryPreset.categoryComparisonKey` 已定义去首尾空白、空分类显示名和 `en_US_POSIX` 的大小写/变音符号/宽度不敏感 folding；应增加最小共享搜索入口，而不是在平台 View 重新实现。
- 共享仓库：`ChronoFocus/Services/FocusStore.swift`。`taskCategories` 提供预设加任务/session 的首次出现去重列表，`categoryMatches` 是选中分类谓词，代表色必须继续来自 `representativeAccentHex(for:)`。

- iOS 已有分类编辑入口：`ChronoFocus/Views/ScheduleView.swift` 的 `TaskEditorView`。现有 `existingCategorySearch`、6 项阈值、option 计数和代表色选择必须保持兼容，必要时只把 key/contains 逻辑委托给共享 helper。

- macOS 已有分类快速新增入口：`ChronoFocusMac/Views/MacScheduleDetailView.swift` 的 `MacExistingCategoryPicker` 和 `MacExistingCategoryOption`。现有搜索 query 的外部预填清除、代表色和“历史”语义不能回归。

## 详细实现要求

### 1. 共享搜索与筛选派生

- 在共享层提供一个非持久化、可由 iOS/macOS 共用的分类搜索入口。可以是 `TaskCategoryPreset` 的静态 helper 或小型值类型，但必须明确区分：
  - 显示名清洗（空白分类显示为 `未分类`）；
  - 搜索 key（空 query 保持空字符串，不能被转成 `未分类`）；
  - 分类名称子串匹配（同一 `en_US_POSIX` folding）；
  - 稳定 option 过滤（先调用既有排序，再按 query 过滤）。
- 使用与 v1.2 一致的长列表阈值 `6`。已有分类编辑器继续按至少 6 个非预设 option 显示搜索；筛选栏应以最终可显示的实际分类 option 数量判断是否显示搜索，不把“全部”虚构为分类，也不因短列表增加无用控件。阈值应放在共享或明确命名的常量中，避免 iOS/macOS 漂移。
- 空 query 返回原始稳定 option 顺序；非空 query 对规范化 key 做子串匹配，保留 `prioritizedFilterOptions` 的顺序和每个 option 的 count/accent/symbol。不要修改 `categories`、`selectedCategory`、草稿或持久化。
- 结果计数必须区分 `matchedCount` 与 `totalCount`：显示 `matchedCount/totalCount`，空 query 为 `totalCount/totalCount`；“全部” chip 始终存在并继续清除分类筛选。
- query 改变时不自动清除已选分类。若当前选中分类不匹配 query，必须仍然保留一个可见、可操作且带明确“当前已选”语义的 option（可在匹配结果外按原顺序末尾 pinned 一次），或提供等价的同色选中摘要清除动作；iOS/macOS 必须采用同一策略，不能让搜索把用户锁在隐藏的筛选状态中。pinned option 不计入 `matchedCount`。
- option 总数由 6 降到 5 时不能留下看不见却仍生效的 query：与现有编辑器相同，低于阈值时返回完整 option；也可保留搜索控件直到 query 被清除，但四处必须一致。selected category 即使已不在 `taskCategories` 中仍应能通过既有摘要/“全部”清除，不能让搜索派生删除用户筛选状态。
- 点击搜索结果继续只切换 `selectedCategory`，不自动开始计时、不修改任务；重复点击已选分类仍清除筛选。清除搜索只清 query，不改变 selected category；“全部”/现有摘要清除只清 selected category，不误删 query，除非当前已有路径明确要求同时离开筛选上下文。

### 2. iOS UI

- 在 `TaskCategoryFilterBar` 与 `TimerTaskCategoryFilterBar` 将横向 chip 包在稳定的纵向布局中：长列表显示搜索 field、`xmark.circle.fill` 清除按钮、结果计数、无结果反馈；短列表保留现有紧凑 chip 体验。
- 两处使用同一 helper 和同一阈值，但保留各自 `countProvider`：日程筛选 count 仍按日期/范围，计时筛选 count 仍按可启动任务；不得把搜索结果数量误当任务数量。
- 搜索 field 使用独立 `@State`，生命周期只属于对应 View；不要新增 `FocusStore` 状态或 UserDefaults。列表/日期/范围重建时 query 可按现有 View 生命周期自然重置，但不能静默改写共享数据。
- 搜索 field、清除按钮、结果计数和无结果状态适配 Dynamic Type，不截断分类名、不挤压邻近内容；清除按钮和 chip 至少 44pt 可操作区。
- 为搜索 field 和清除按钮补齐 VoiceOver label/hint、Voice Control input labels；结果计数读出当前匹配/总数，无结果读出“没有匹配的分类”。保留 chip 的 selected trait、分类名、任务数和重复点击清除提示。
- 日程的分类摘要、空态、新增此分类与 timer handoff 继续读取原 `selectedCategory`；搜索 query 不得改变新增表单的 `initialCategory` 或 handoff request。

### 3. macOS UI 与快照

- `MacCategoryFilterBar` 的真实路径和 `macSnapshotRendering` 静态路径必须共享同一个过滤后的 option 派生结果、matched/total 计数、选中/pinned 规则和无结果文案；不要为快照写第二套分类搜索算法。
- 在 `MacScheduleDetailView` 的任务列表和 `MacTimerDetailView` 的待办队列确认 query 的 View ownership、筛选切换和 handoff/快速新增边界。计时运行中仍不可切换任务；搜索只能改变可见 chip，不得替换当前 TimerEngine 任务。
- macOS 已有分类快速新增搜索继续使用现有 v1.2 helper/阈值和外部预填清除；不要把筛选 query 与 `existingCategorySearchQuery` 混成一个状态。已有分类选中后仍更新草稿分类和代表色，不保存搜索字串。
- 现有 `macCategoryComparisonKey` 已是共享规则薄包装，不要求删除。将 query folding 委托共享搜索入口时，确认已有分类 picker、筛选 predicate、快照静态视图仍按各自显示名/空查询语义工作；不得把空 query 误清洗为“未分类”，也不得留下平台语义漂移。
- 更新 `scripts/render_mac_snapshots.swift` 的云端 fixture，使正式 `detail-schedule.png` 或 `detail-timer.png` 在至少 6 个非预设分类可用时展示搜索 query、匹配/总数和至少一个可见结果；应覆盖 query 与 selected category 一致的非空状态，并检查无空白、黄色占位、明显裁切、重叠或关键文本截断。
- 正式快照仍只允许 `mini-timer.png`、`detail-timer.png`、`detail-schedule.png`、`detail-analytics.png`、`detail-settings.png` 五项；临时探索图不得写入正式 artifact manifest。快照 fixture 不得改变产品默认数据之外的共享持久化格式。

## 风险与禁止项

- 不要把空 query 送入“空分类 -> 未分类”的显示清洗函数，否则搜索会错误隐藏全部分类；必须保留独立空 query 语义。
- 不要在过滤后按名称/匹配度/数量再次排序，否则会破坏 v1.0/v1.1/v1.4.8 的首次出现和颜色稳定性。
- 不要让 query 覆盖 `selectedCategory`，不要在搜索输入时自动选择、自动开始计时或修改任务；selected 被 query 隐藏时必须仍可见且可清除。
- 不要让 iOS 和 macOS 各自保留不同的分类 folding/key helper；平台差异只能存在于控件和快照安全渲染边界。
- 不要为测试方便硬编码 marker、伪造日志、放宽 negative fixture、复用旧 artifact 或把包内 metadata 当作 API 证据。
- 禁止本地项目测试、validator、YAML 检查、Xcode、`xcodebuild`、`simctl`、Simulator 和浏览器；禁止 reset/checkout/revert、删除或覆盖他人改动和用户未跟踪文件；所有测试/验收只走 GitHub Actions 与 `gh`。
