## 2. 背景与根因

`runTimerEngineBoundaryTests` 先生成一个计划项，再执行：

1. 开启 `autoGeneratePomodoroPlan`。
2. 保存 `originalPlanItem`。
3. 通过 `FocusStore.setTaskEnabled(planTask, enabled: false)` 停用计划项所属任务。
4. 调用 `TimerEngine.startPlanItem(planItem)`。

当前真实实现的行为是：

- `FocusStore.setTaskEnabled(..., enabled: false)` 会调用 `regeneratePlanIfNeeded()`。
- 自动生成计划只纳入启用任务，因此停用任务后，原计划项可能已经从 `store.pomodoroPlan` 中移除。
- `TimerEngine.startPlanItem(_:)` 先通过 `store.startableTask(for:)` 复核任务是否仍可启动；任务已停用时直接返回，不创建 `activeTimer`，也不会调用 `store.markPlanItemStarted(item)`。
- `FocusStore.markPlanItemStarted(_:)` 只有在计划项仍存在且 `TimerEngine` 的 startable guard 通过时才会修改 `scheduledStart`。

因此，当前断言把“计划项因停用任务被合法重生成移除”错误当成了“计划项被标记开始”。失败发生在测试期望，不是 `FocusStore` 或 `TimerEngine` 的业务逻辑错误。

## 5. 当前架构依据

### 5.1 共享数据和计时边界

- `ChronoFocus/Services/FocusStore.swift` 是任务、设置、会话、计划和活跃计时快照的唯一共享数据仓库。
- `FocusStore.setTaskEnabled` 修改任务启用状态；自动计划开启时通过 `regeneratePlanIfNeeded` 重新生成计划。
- `FocusStore.generatePomodoroPlanFromSchedule` 只为未完成且启用的任务生成 `PomodoroPlanItem`，所以停用任务对应的原 item 可能不再存在。
- `FocusStore.markPlanItemStarted` 通过 item ID 定位计划项，只修改 `scheduledStart` 和 `scheduledEnd`；找不到 item 时直接返回。
- `ChronoFocus/Services/TimerEngine.swift` 是唯一计时状态机。`startPlanItem` 先调用 `store.startableTask(for:)`，失效任务直接返回，再执行 `markPlanItemStarted`、同步时长和 `start()`。
- `scripts/test_mac_core.swift` 通过 fake 平台服务运行共享 `TimerEngine` 边界测试，不是产品逻辑的第二实现。

### 5.2 本轮测试合同

本轮合同只验证两件事：无效计划项不能创建 `activeTimer`；若原 item 仍留在计划中，其开始时间不能被无效启动路径改写。计划项因自动重生成消失是合法状态，不应被测试强制保留。
