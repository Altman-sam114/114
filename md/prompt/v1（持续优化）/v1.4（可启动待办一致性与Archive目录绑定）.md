# v1.4 可启动待办一致性与 Archive 目录绑定

## 1. 版本号与分配依据

- 版本号：`v1.4`。
- 分配依据：v1.3 已完成“日程分类接力到计时”并由最新证据 commit `2477407c21faf2e131e456fd19113344465b64d9` 的 GitHub Actions run `30323180673`（attempt `1`）、artifact id `8674780603` 复判为 `129 PASS / 0 FAIL`；本轮沿用 v1 持续优化序列递增。
- 本轮角色：Agent A 定义产品与 CI 信任边界；Agent B 必须基于最新 `origin/main` 实现、提交并直接 push；Agent C 只接受本轮最新 commit 对应的授权 `push` run、原始 API JSON、原始 ZIP 和与 ZIP 完整绑定的解包目录。
- 版本目标由两项独立新增 PASS 组成：`Startable task consistency contracts verified.` 对应项目契约，以及 `artifact archive extracted directory binding` 对应 archive 解包目录绑定；完整第四模式预期从 129 增至 `131 PASS / 0 FAIL`。

## 2. 背景

v1.3 已要求日程接力在消费时重新查询当前数据并排除已完成、已停用或已删除任务，但计时页直接选择、Mac 小窗选择、计划项启动和计时主控仍未共享同一个“可启动待办”定义：

- `FocusStore.upcomingTasks()` 只表达未完成及排序语义，不能被改成“可启动”，否则会让日程页失去停用任务及其重新启用入口。
- iOS `TimerView`、macOS 详细计时队列和 `MacMiniTimerView` 仍可能从 `upcomingTasks()` 展示或选择停用任务。
- `TimerEngine.selectTask(_:)`、`startPlanItem(_:)` 和 `start()` 需要在 View 之后再次复核当前 store，防止点击到执行之间任务被完成、停用或删除。
- 空闲时当前选择失效后，标题、主控语义和选择标记可能继续指向旧任务；运行中则必须继续以 `ActiveTimerSnapshot` 为真相，不能因任务随后变化而清除正在运行或暂停的会话。

当前 archive 完整模式虽然核对原始 ZIP 的字节数、SHA-256 与 ZIP 结构，也复判调用方传入的解包目录内容，但尚未证明“这个目录就是这个 ZIP 的解包结果”。攻击者或误操作可把合法 ZIP 与另一份同身份、可通过目录检查的目录组合交给 validator。v1.4 必须增加包到目录的逐路径内容绑定，关闭该替换空间。

## 3. 目标

### 3.1 可启动待办一致性

1. 保持 `FocusStore.upcomingTasks()` 的现有实现与语义不变。
2. 在 `FocusStore` 新增唯一共享查询：
   - `startableTasks()`：基于 `upcomingTasks()`，仅返回 `isEnabled == true` 的当前未完成任务，并保持既有排序。
   - `startableTask(for:)`：按可选 id 返回 store 中当前仍可启动的任务，否则返回 `nil`。
3. iOS `TimerView`、macOS `MacTimerDetailView`/任务队列、`MacMiniTimerView` 的队列、分类计数、选择入口与空态统一使用 `startableTasks()`；日程页面继续展示停用任务并允许重新启用。
4. v1.3 iOS/macOS handoff 不再自行拼接 `upcomingTasks().filter(\.isEnabled)`，统一通过 `startableTasks()` / `startableTask(for:)` 重新验证 preferred task 和分类首个任务。
5. `TimerEngine.selectTask(_:)`、`startPlanItem(_:)` 和 `start()` 都以 `FocusStore` 当前可启动查询作为最终防线，不信任传入的旧 `FocusTask` 或旧 `selectedTaskID`。
6. 增加集中式空闲选择 reconcile：空闲时已选任务变成已完成、停用或删除，必须清除为“自由专注”；任务变化以及停止、完成等进入空闲状态后都要收敛。运行中或暂停中不得清除 `selectedTaskID`、当前标题或 `ActiveTimerSnapshot`。
7. 空闲 `start()` 遇到失效选择时先 reconcile，再按自由专注启动；`startPlanItem(_:)` 的任务失效时不得标记计划开始、不得启动自由专注或新会话。
8. 双平台空态、计数、VoiceOver 与 Voice Control 文案必须明确表达“可启动待办”，不能把停用任务计入计时队列数量。

### 3.2 Archive 解包目录绑定

1. 保留 validator 四种调用模式：目录-only、archive 三参数、archive + artifact metadata、archive + artifact metadata + run metadata；不新增必填 CLI 参数，不破坏现有参数依赖关系。
2. 当且仅当完整 archive 三参数存在时，使用第一个位置参数的 artifact 解包目录与 `--archive` 指向的原始 ZIP 做结构化绑定；目录-only 模式保持兼容且不伪造该 PASS。
3. 通过标准库或等价结构化 ZIP API 安全枚举中央目录；不得只依赖 `unzip -Z1`、文件名文本输出或调用方现有目录自证。
4. 在 validator 自己创建的全新唯一临时目录中安全解包原始 ZIP，绝不覆盖、写入、修补或删除调用方目录及原始证据。
5. 对 ZIP 入口先做 fail-closed 校验，再写入临时目录：
   - 拒绝绝对路径、盘符路径、反斜杠、NUL、空组件、`.`、`..`、规范化后逃逸和任何 traversal。
   - 拒绝重复原始路径、重复规范化路径、文件/目录前缀冲突及会发生覆盖的条目。
   - 只允许普通文件和目录；拒绝 symlink、hard link、device、FIFO、socket 及未知特殊类型。
   - 不跟随 symlink；每个输出路径必须保持在临时根目录内，并受合理 entry 数、单文件及总解压大小上限保护。
6. 对安全临时解包树和参数目录分别执行不跟随 symlink 的递归枚举，比较精确相对路径集合；逐路径比较类型，普通文件再比较 byte size 与 SHA-256。隐式父目录必须规范化为同一目录树语义，额外、缺失、类型不同、大小不同或 digest 不同均失败。
7. 成功时输出精确 PASS：`PASS artifact archive extracted directory binding`；失败时输出对应 `FAIL artifact archive extracted directory binding`，且不得继续把不绑定的目录判为完整模式通过。
8. 增加定向错配负例：保持原始 ZIP、archive size/digest/ZIP integrity、artifact metadata 和 run metadata 均合法，只对参数目录中的一个普通文件做等长内容替换，使其他 archive/API PASS 保持通过且仅目录绑定项失败。
9. 另设最小 ZIP 安全负例，分别证明 traversal、重复路径和特殊文件被绑定检查拒绝；fixture 只能使用全新临时输入，不能修改真实证据或仓库文件。

## 4. 非目标

- 不修改、重命名或收窄 `FocusStore.upcomingTasks()`；不让日程页隐藏停用任务。
- 不新增任务模型字段、UserDefaults key、数据迁移、分类规则、任务排序或计划排序。
- 不自动启用停用任务，不自动恢复已完成任务，不把失效计划项降级成自由专注。
- 不改变运行中或暂停中 `ActiveTimerSnapshot` 的恢复、通知、Live Activity、剩余时间、任务标题或分类语义。
- 不在 View 中复制第二套可启动判定；View 不得直接写 `engine.selectedTaskID`。
- 不改变 v1.3 handoff 的 UUID、分类恢复、精确失效清除、运行中只浏览及不自动开始规则。
- 不改变 artifact 名称、artifact 内容清单、manifest/index/run context process version、Run API 14 项或 artifact metadata 8 项语义。
- 不要求目录-only 模式拥有原始 ZIP，不移除或弱化 archive byte count、SHA-256、ZIP integrity 三项现有验证。
- 不引入第三方 Swift、Ruby 或 ZIP 依赖；优先使用系统/标准库结构化 API，并保持 GitHub Actions 与 Agent C 当前环境可执行。
- 不读取、编辑、暂存或提交 `md/1.md` 与 `md/通用云端迭代升级提示词.md`。

## 5. 当前架构依据

### 5.1 Store 与计时边界

- `ChronoFocus/Services/FocusStore.swift` 是任务唯一仓库；`upcomingTasks()` 已被日程、计划和统计等不同语义复用，因此必须保留，并在旁边新增更窄的 startable API。
- `ChronoFocus/Services/TimerEngine.swift` 是唯一计时状态机；View 只表达选择意图，真正选择、计划启动、普通启动与空闲失效收敛必须在这里做最终复核。
- `ActiveTimerSnapshot` 是运行中/暂停中会话真相；任务在计时期间被停用、完成或删除，不得中断或改写既有 snapshot。

### 5.2 iOS 与 macOS 入口

- `ChronoFocus/Views/TimerView.swift` 的队列、分类筛选、计数、空态和 v1.3 handoff 都应从 `store.startableTasks()` 派生。
- `ChronoFocusMac/Views/MacTimerDetailView.swift` 的详细队列和 handoff resolver 使用同一 API。
- `ChronoFocusMac/Views/MacMiniTimerView.swift` 当前展示并选择 `upcomingTasks().prefix(3)`，必须改为可启动集合；小窗只负责展示和调用 `engine.selectTask`。
- `ChronoFocus/Views/ScheduleView.swift` 与 `ChronoFocusMac/Views/MacScheduleDetailView.swift` 仍承担完成、停用和重新启用管理，不得改成 startable-only 列表。

### 5.3 Artifact 信任边界

- `scripts/validate_ci_artifact.rb` 的第一个位置参数是待复判的已解包 artifact 目录，`--archive` 是包外原始 ZIP；v1.4 的新增检查必须证明两者内容同源。
- `scripts/verify_project.sh` 负责成功 fixture、安全负例、定向错配和 marker 缺失路径；fixture 不能依赖历史 artifact 或网络。
- 原始 `run-api.json`、`artifacts-api.json`、ZIP 及 Agent C 证据目录属于只读证据；validator 只能另建临时解包树进行比较。

## 6. Agent B 实现步骤

### 6.1 同步与范围确认

1. 执行 `git fetch origin`、`git switch main`、`git pull --ff-only origin main`，确认 HEAD 为最新 `origin/main`。
2. 只审阅工作区状态和相关源码；不得读取或纳入两份用户文件，不得回滚、删除或覆盖任何不明改动。
3. 阅读本提示词、`AGENTS.md`、v1.3 最终记录、`md/flow/*`、`md/test/test.md`、相关 Swift/CI 脚本后再实现。

### 6.2 FocusStore 可启动查询

1. 在 `FocusStore` 邻近 `upcomingTasks()` 新增 `startableTasks()`，实现必须直接复用 `upcomingTasks()` 的未完成和排序结果，再过滤 `isEnabled`。
2. 新增 `startableTask(for id: UUID?)`；`nil`、不存在、已完成或已停用均返回 `nil`，合法时返回 store 中当前对象而不是调用方旧副本。
3. `scripts/test_mac_core.swift` 增加小数据测试：排序保持、停用排除、完成排除、删除后失效、重新启用后恢复、`upcomingTasks()` 仍包含未完成停用任务。

### 6.3 TimerEngine 最终防线与 reconcile

1. `selectTask(_:)` 保留运行中拒绝切换；传入非 nil 时按 id 重新取 `store.startableTask(for:)`，只选择当前合法对象。非法旧对象不得成为选择；若当前选择本身已失效则统一 reconcile，不能误清除另一个仍合法选择。
2. 提供单一 `reconcileIdleSelectedTask()` 或等价集中入口：仅在非运行/非暂停状态检查 `selectedTaskID`，失效时通过引擎内部统一路径清为 `nil` 并把标题恢复“自由专注”。
3. 监听或在所有必要状态入口调用 reconcile，至少覆盖任务数组变化、App/视图恢复、`stop`、自然完成、跳过/完成流转结束及其他进入空闲的路径。实现可使用既有 Combine 边界，但不得形成 View 自己维护的第二套选择状态。
4. `start()` 在创建 snapshot 前调用 reconcile，并只用 `startableTask(for:)` 解析空闲选择；失效选择按自由专注创建新会话，snapshot 不得携带旧任务 id/title/category。
5. `startPlanItem(_:)` 必须同时验证非运行、计划项当前任务存在且仍可启动；失败时不标记计划项、不创建 snapshot、不退化启动自由专注。
6. 运行中或暂停中任务数据变化时 reconcile 必须 no-op，既有 `selectedTaskID`、标题和 snapshot 保持；当前会话完成后的后续空闲状态再按规则收敛。

### 6.4 iOS/macOS UI 与 v1.3 接力

1. iOS `TimerView` 把队列、分类过滤、分类计数、展开数量与空态数据源改为 `startableTasks()`；任务选择仍只调用 `engine.selectTask`。
2. Mac 详细计时队列执行同样替换，现有分类摘要、空态和快照布局保持；不得顺手实现其他队列重构。
3. `MacMiniTimerView` 的总数、前三项、selected 状态和点击选择使用 startable 集合；停用任务仍可在 Mac 日程列表重新启用。
4. iOS/macOS v1.3 handoff 通过 startable API 重新查询：分类摘要选首个当前合法任务，preferred id 只接受同分类合法任务；精确目标失效清除旧空闲选择，运行中仍只恢复分类、不清除当前任务或 snapshot。
5. 双端计时队列无结果时文案改为“暂无可启动待办，仍可启动自由专注”或同等明确表述；分类空态、计数及辅助功能标签不得声称包含停用任务。
6. 日程两端继续基于原有 `store.tasks` / `upcomingTasks()` 语义展示停用任务、启用开关和操作；加入 CI contract 防止误把日程改成 `startableTasks()`。

### 6.5 Startable CI contract

1. `scripts/verify_project.sh` 增加结构化源码和核心测试契约，锁定 `startableTasks/startableTask`、`upcomingTasks` 不变、三处计时 UI 接线、v1.3 handoff 复用、三项 TimerEngine 最终防线、空闲 reconcile、运行中 snapshot 保护及日程保留停用任务。
2. 明确拒绝计时 UI 回退到直接 `upcomingTasks()` 作为可选队列、View 直接写 `selectedTaskID`、`start()` 通过 `store.task(for:)` 接受失效选择，或 `startPlanItem` 在任务失效时继续标记/启动。
3. 成功时输出精确 marker：`Startable task consistency contracts verified.`。
4. 增加只移除该 marker 的负向 fixture；validator 必须只新增并复判 `PASS verify_project startable task consistency contracts`，不得把别的 marker 当替代证据。

### 6.6 Archive extracted directory binding

1. 在 `scripts/validate_ci_artifact.rb` 中把绑定检查放在 archive 参数组基础安全校验之后、完整模式成功结论之前；archive 不合法时不得尝试把参数目录与其绑定。
2. 使用结构化 ZIP entry 元数据构造规范路径和类型清单，先完成 traversal、重复、覆盖冲突、特殊文件和资源上限检查，再安全写入 validator 自有的全新临时目录。
3. 禁止调用普通自动解包后才补查路径；每个 entry 的目标路径必须在写入前验证仍位于临时根目录。不得跟随输入目录或临时树中的 symlink。
4. 建立参数目录与临时树的独立 manifest：相对路径、类型、普通文件 byte size、SHA-256；目录集合与普通文件集合都必须精确一致。
5. 绑定成功输出 `PASS artifact archive extracted directory binding`。任何异常、解析失败、不支持 entry、资源上限、路径差异或文件内容差异均 fail closed，输出目标 FAIL 并以非零状态结束。
6. 临时树只能包含 validator 本次创建的派生内容；失败时不得删除或修改原始 ZIP、API JSON、参数目录或 Agent C 证据。不得把临时树冒充原始下载证据。
7. `scripts/verify_project.sh` 增加：
   - archive 成功 fixture，证明 archive 三参数及更强两种 metadata 模式得到绑定 PASS；
   - 参数目录单文件等长篡改 fixture，证明三项 archive integrity 仍 PASS、仅 binding FAIL；
   - traversal ZIP、重复路径 ZIP、特殊文件 ZIP 定向拒绝 fixture；
   - 只移除绑定 PASS 文本的 marker/日志负例，使 artifact validator 的对应复判失败。
8. `scripts/validate_ci_artifact.rb` 对自身云端日志增加精确 `PASS artifact archive extracted directory binding`；不得把该运行时 PASS 伪装成 `verify_project` marker。

### 6.7 文档、提交与云端循环

1. 同步文档后只暂存本轮相关文件，明确排除两份用户文件。
2. 提交信息使用：`v1.4: 统一可启动待办与归档目录绑定`。
3. push 前确认分支为 `main`、目标为 `origin/main`；直接 push 触发 `ChronoFocus CI Results`。
4. 云端失败不回滚；保留证据并在 `main` 追加修复 commit，直到 Agent C 对最新 run 完成第四模式复判。

## 11. 风险与禁止项

- 最大产品风险是误改 `upcomingTasks()` 导致日程隐藏停用任务；必须用 core test 和源码 contract 双重锁定。
- 最大状态风险是 store 变化监听在运行中清除任务；所有 reconcile 必须先判断运行/暂停状态，绝不改写活跃 snapshot。
- `start()` 将失效选择降为自由专注，而 `startPlanItem()` 必须失败退出；两条路径不得混淆。
- 不得只在 UI 过滤停用任务而遗漏 `TimerEngine` 最终防线，也不得只改引擎而保留错误计数、空态和可访问文案。
- ZIP entry 名称属于不可信输入；不得先用普通 `unzip` 写盘再检查 traversal，不得跟随 symlink，不得允许重复 entry 后写覆盖。
- 不得只比较 manifest/index 身份或文件名集合；绑定必须比较独立临时解包树与参数目录的精确类型、大小和 SHA-256。
- 不得删除、覆盖或修补原始 API JSON、ZIP、调用方解包目录、失败证据或历史验收目录；默认不执行删除操作。
- 不得下载历史 artifact、DerivedData、模型或大体积无关数据；临时解包必须有资源上限。
- 不得放宽 metadata 文件普通文件/非 symlink/1 MiB 边界，不得让包内字段自证 API size/digest、run status 或授权来源。
- 不得修改两份用户文件，不得把它们加入 status 清理、暂存、commit 或 push。
- 云端失败不得回滚已 push commit；只允许在 `main` 追加最小修复并重新走完整 Agent C 验收。
