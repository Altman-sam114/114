# v0.99：iOS 计时队列展开与 Artifact API 元数据复判

## 1. 版本号与分配依据

- 版本号：`v0.99`。
- 分配依据：`update_log.md` 和 `md/prompt/README.md` 当前最新正式闭环版本为 v0.98，因此本轮顺序递增为 v0.99。
- 固定提交信息：`v0.99: 展开iOS计时队列并复判Artifact API`。
- 协作分支固定为 `main`，实现、提交、push、GitHub Actions 和 Agent C 验收均只针对最新 `origin/main`。

## 2. 背景

### 2.1 iOS 计时队列

`ChronoFocus/Views/TimerView.swift` 的计时页会显示当前筛选后的待办总数，但任务列表固定使用 `filteredUpcomingTasks.prefix(4)`。当待办超过 4 项时，用户能看到总数，却无法在计时页访问第 5 项及之后的待办。分类筛选后同样存在该问题。

本轮需要保留默认紧凑展示，同时提供明确的展开和收起入口。展开控制只是列表显示状态，不得进入 `TimerEngine`，不得改变当前任务、计时状态或持久化模型。

### 2.2 Artifact API 外部元数据

v0.97 已让 `scripts/validate_ci_artifact.rb` 支持可选的 `--archive`、`--archive-size`、`--archive-digest` 完整参数组，并复算原始 ZIP 的 byte count、SHA-256 和 ZIP 结构。当前 Agent C 仍需人工从 GitHub artifacts API 响应中拆出 id、name、size、digest、expired 和 workflow run 身份，validator 没有读取原始响应，也无法机器交叉核对“唯一 artifact -> 下载 ZIP -> manifest/run context”的完整身份链。

本轮新增可选 `--artifact-metadata JSON`，让 Agent C 保存 GitHub artifacts API 原始响应，并由 validator 使用结构化 JSON 解析复判。API JSON 是 Agent C 本地保留的外部证据，不得加入 GitHub Actions 上传内容。

## 3. 本轮目标

### 3.1 UI 目标

1. iOS 计时待办队列默认只展示前 4 项，维持当前紧凑布局。
2. 当筛选后待办超过 4 项时，在列表后显示“显示其余 N 项”控制；展开后显示全部筛选结果，并把控制切换为“收起”。
3. 分类筛选发生变化时自动恢复默认收起状态。
4. `filteredUpcomingTasks.count` 发生变化时自动恢复默认收起状态，包括新增、完成、删除或其他仓库更新导致的数量变化。
5. 计时运行中仍允许展开和收起列表，但所有任务行继续禁用，不允许切换当前待办。
6. 展开控制具备至少 44pt 点击高度，并完整支持动态字体、VoiceOver label/value/hint 和 Voice Control 输入标签。

### 3.2 CI 目标

1. Validator 新增可选 `--artifact-metadata JSON` 文件参数。
2. 结构化解析 GitHub run artifacts API 原始响应，严格确认响应中只有一个 artifact。
3. 复判该 artifact 的 id、name、size、digest、expired 和 `workflow_run.id/head_sha/head_branch`，并与现有 commit/run/branch、预期 artifact 名称和 archive 参数交叉核对。
4. 保持目录-only 和既有 archive 三参数调用兼容。
5. 增加独立 PASS、项目验证 marker、成功 fixture 和精确负向 fixture。
6. 将 Agent C 原始 API JSON 的 `.part` 保存、无覆盖原子改名和原始 ZIP 下载流程写入协作文档。

## 4. 非目标

- 不修改 `TimerEngine`、`FocusStore`、共享模型、持久化格式或计时流转规则。
- 不改变待办排序、分类筛选语义、当前任务选择规则或分类摘要/空态行为。
- 不给 macOS 队列增加同类展开功能；本轮 UI 范围仅为 iOS `TimerView`。
- 不增加分页、搜索、拖拽排序、批量任务操作或新的导航页面。
- 不让 validator 发起网络请求、调用 GitHub CLI、读取 token 或认证 GitHub 响应来源。
- 不新增 artifact 文件、上传路径、manifest/index entry、缓存、模型、历史结果包或重复 ZIP。
- 不把 artifacts API JSON 放进 `ci-results/`、解包目录或 GitHub Actions artifact。
- 不声称 artifacts API 的 `workflow_run` 直接证明 run attempt；该响应没有 `run_attempt` 字段。

## 5. 当前架构依据与边界

### 5.1 UI 边界

- `TimerView.filteredUpcomingTasks` 是 `FocusStore.upcomingTasks()` 加当前分类筛选后的派生结果，应继续作为显示来源。
- `TimerEngine` 是唯一计时状态机；列表展开只是 `TimerView` 的临时展示状态。
- 当前任务行通过 `.disabled(engine.isRunning)` 禁止运行中切换；本轮必须保留该边界。
- 分类筛选继续由 `TimerTaskCategoryFilterBar` 和 `selectedTaskCategory` 管理，不创建第二套分类状态。
- `TaskRow` 的任务名、分类、选中状态、运行状态、hint 和 Voice Control 语义保持不变。

### 5.2 CI 边界

- `--commit`、`--run-id`、`--attempt` 继续为必填，`--branch` 默认 `main`。
- `--archive`、`--archive-size`、`--archive-digest` 继续全有或全无。
- `--artifact-metadata` 是可选增强输入，但一旦提供，必须同时提供完整 archive 三参数组。
- 不提供 metadata 时，现有目录-only 和 archive 模式的参数、PASS/FAIL 和退出语义必须保持兼容。
- API size/digest 是包外信任输入；manifest、index 或 ZIP 内字段不得反向自证 API 元数据。
- 原始 API 响应只能证明文件内容内部与调用参数一致；其真实来源仍由 Agent C 的授权账号、仓库 endpoint、run 选择和下载过程保证。

### 6.2 iOS 队列展示状态

在 `TimerView` 内增加单一临时展开状态，例如 `isTaskQueueExpanded`，并以明确的 4 项阈值派生：

- 收起时展示 `filteredUpcomingTasks` 前 4 项。
- 展开时展示全部 `filteredUpcomingTasks`。
- 剩余数量严格为 `max(filteredUpcomingTasks.count - 4, 0)`。
- 仅当筛选后数量大于 4 时显示展开/收起控制。
- 初次进入和数量不超过 4 时不得显示无意义的展开控制。

### 6.3 重置规则

必须对以下两个变化源分别接线，统一把展开状态重置为 `false`：

- `selectedTaskCategory` 变化，包括从全部切到分类、分类间切换、再次点击清除和空态清除筛选。
- `filteredUpcomingTasks.count` 变化，包括新增当前分类待办、完成任务、删除任务或外部仓库刷新。

不得仅在点击筛选 chip 时重置，否则其他清除入口和数据更新会遗漏。重置只影响列表展开状态，不改变分类、当前任务或计时。

### 6.4 展开/收起控制

- 收起文案为动态的“显示其余 N 项”，N 必须来自当前筛选后的剩余数量。
- 展开文案为“收起”。
- 可使用系统 `chevron.down` / `chevron.up` 图标辅助表达状态，不手绘图标。
- 控件最小高度至少 44pt，布局宽度稳定，不因文案、图标或点击状态导致列表跳动。
- 使用语义字体并允许文字合理换行；不得依赖固定字号、截断最长文案或 viewport 字号缩放。
- 展开按钮不得被 `engine.isRunning` 禁用，也不得放进随任务行整体禁用的父容器。
- 任务行继续逐行 `.disabled(engine.isRunning)`；运行中展开后新增显示的任务行同样不可选择。

### 6.5 辅助功能

- Voice Control input labels：至少包含“显示其余N项”“显示更多待办”“展开待办”。

- VoiceOver hint：说明收起后显示前 4 项。
- Voice Control input labels：至少包含“收起”“收起待办”“收起待办列表”。

动态 label/value/hint 必须基于当前筛选计数，不得缓存旧分类的 N。可访问元素应是一个明确按钮，避免图标和文字被 VoiceOver 重复朗读。

### 6.7 `--artifact-metadata JSON` 参数与安全约束

`JSON` 表示 GitHub `GET /repos/{owner}/{repo}/actions/runs/{run_id}/artifacts` 的原始响应文件路径，不接受内联 JSON。

参数文件必须：

- 非空。
- 不大于 1 MiB，即 `1_048_576` bytes。
- 使用 `lstat` 或等价方式确认是普通文件并明确拒绝 symlink。
- 使用 UTF-8 和 `JSON.parse` 结构化解析。
- 禁止 `eval`、YAML 反序列化、shell 拼接、字段 grep 或网络请求。

未知的 GitHub 未来扩展字段可以保留，不要求顶层或 artifact 对象精确键集；但所需字段必须存在、类型严格且值匹配。

参数组合规则：

| Metadata | Archive 三参数 | 结果 |
| --- | --- | --- |
| 全无 | 全无 | 保持目录-only 兼容 |
| 无 | 全有 | 保持 v0.97 archive 调用兼容 |
| 有 | 全有 | v0.99 完整复判模式 |
| 有 | 非全有或全无 | 参数错误，拒绝 |
| 无 | 部分 archive 参数 | 维持既有参数错误 |

metadata 单独提供时必须清楚报告需要 `--archive`、`--archive-size` 和 `--archive-digest`；不得悄悄降级为只验证 JSON。

### 6.8 API 响应结构化复判

顶层必须是 JSON object，并满足：

- `total_count` 严格为整数 `1`。
- `artifacts` 严格为数组且长度为 `1`。
- `total_count` 与数组长度一致。

唯一 artifact 必须满足：

- `id` 严格为正整数。
- `name` 严格等于现有 `expected_artifact_name`。
- `size_in_bytes` 严格为正整数，且等于 `--archive-size`。
- `digest` 符合 `sha256:` 加 64 位十六进制；大小写归一后等于 `--archive-digest`。
- `expired` 严格为 JSON boolean `false`，不得接受字符串 `"false"`、`nil` 或 truthy/falsy 转换。
- `workflow_run` 严格为 object。
- `workflow_run.id` 等于 `--run-id`。
- `workflow_run.head_sha` 等于 `--commit`。
- `workflow_run.head_branch` 等于 `--branch`。

现有实际 ZIP 检查继续独立执行：

- `artifact archive byte count` 把实际文件大小与 `--archive-size` 比较。
- `artifact archive sha256 digest` 复算实际文件摘要并与 `--archive-digest` 比较。
- `artifact archive zip integrity` 使用安全参数数组调用 `unzip -t`。

因此 API JSON、CLI archive size/digest 和实际 ZIP 必须三方一致。artifact id 没有现有 CLI 对照字段，validator 负责确认其唯一且为正整数；Agent C 必须使用同一原始 JSON 中的 id 作为下载 endpoint。validator 无法回溯 HTTP 请求历史，文档不得夸大这一点。

GitHub run artifacts API 的 `workflow_run` 不包含 `run_attempt`。attempt 继续通过以下证据关联：

- `--attempt` 必填参数。
- 预期 artifact 名称中的 `attempt<N>`。
- manifest、index、`ci-run-context.txt` 的既有 runAttempt 复判。
- Agent C 对最新 workflow run API 的 run attempt 核对。

不得新增不存在的 API attempt 检查，也不得声称 `workflow_run.id` 能区分 rerun attempt。

### 6.9 Metadata 独立 PASS 与 marker

完整 metadata 模式至少输出以下独立检查名：

```text
PASS artifact metadata response shape
PASS artifact metadata unique artifact
PASS artifact metadata id
PASS artifact metadata name
PASS artifact metadata byte count
PASS artifact metadata sha256 digest
PASS artifact metadata not expired
PASS artifact metadata workflow run
```

各检查失败时必须输出同名 `FAIL`，让 Agent C 能区分响应形状、唯一性、身份、归档和 workflow run 错误。JSON 无法解析时应给出明确且有界的验证失败信息，不输出原始响应全文或认证信息。

新增项目验证 marker：

```text
CI artifact API metadata contracts verified.
```

Validator 对应：

```text
PASS verify_project ci artifact API metadata contracts
```

不得改 `.github/workflows/ci-results.yml` 的 artifact path、manifest/index 文件清单、上传名称或 retention；API JSON 只属于 Agent C 下载证据。

### 6.10 Metadata fixtures

成功 fixture：

- 在 archive fixture 临时目录中创建小型原始风格 API JSON，不得放进 artifact 解包 fixture 根目录。
- 使用 `total_count=1` 和单一 artifact。
- id 为正整数；name、size、digest、expired、workflow run id/head SHA/head branch 与 fixture 参数完全一致。
- 使用 metadata 加完整 archive 参数运行 validator。
- 断言八个 metadata PASS、三个 archive PASS 和新 marker PASS。

兼容 fixture：

- 既有目录-only fixture 继续成功。
- 既有完整 archive 三参数 fixture 继续成功。
- metadata 不带完整 archive 参数必须以参数错误退出，并列出缺失参数。

负向 fixture 至少覆盖：

1. 非法 JSON、顶层数组或空文件。
2. 文件超过 1 MiB、非普通文件和 symlink 拒绝路径。
3. `total_count` 为零或二、artifact 数组为空或含两个元素、计数与数组长度不一致。
4. id 为零、负数或字符串。
5. name 与预期 artifact 名称不匹配。
6. metadata size 与 archive size 参数不匹配。
7. metadata digest 与 archive digest 参数不匹配。
8. expired 为 `true` 或非 boolean。
9. `workflow_run` 缺失或类型错误。
10. workflow run id、head SHA、head branch 分别篡改。
11. `CI artifact API metadata contracts verified.` marker 缺失。

metadata size/digest 负向 fixture 应保持实际 ZIP 与原 archive 参数一致，并断言三个 archive 检查继续 PASS，从而证明失败只来自 API 元数据交叉核对。fixture 必须保持小数据量，不复制真实大 artifact。

### 6.11 Agent C 原始 JSON 与 `.part` 流程

Agent C 必须：

1. 确认 GitHub CLI active account 为 `Altman-sam114`。
2. 获取最新 `origin/main` commit 对应 workflow run id 和 run attempt，只选择该 run 的唯一必要 artifact。
3. 创建全新的 `/private/tmp/chronofocus-c-review-<run_id>-<unique>/`；任何目标文件、目录、`.part`、最终 JSON、ZIP 或解包目录已存在时，停止并使用新的唯一目录。
4. 将 artifacts API 响应原样保存为 `artifacts-api.json.part`，不得通过 `jq`、Ruby 或字符串处理重建响应。
5. 请求成功、文件非空且最终 `artifacts-api.json` 不存在后，在同一文件系统无覆盖原子改名为 `artifacts-api.json`。
6. 使用结构化解析从该原始 JSON 取得唯一 artifact id/name/size/digest/expired/workflow run 字段；路径文件名使用可信输入计算出的预期 artifact name，不直接信任任意 API name。
7. 使用同一 JSON 的 artifact id 下载到 `<artifact-name>.zip.part`，启用失败即退出、跟随重定向和有限重试。
8. 在 ZIP `.part` 上核对 API size、SHA-256 和 ZIP 结构；全部通过且最终 ZIP 不存在后，同文件系统无覆盖原子改名为 `<artifact-name>.zip`。
9. 解包到全新目录，再把解包目录、commit/run/attempt、原始 ZIP、API size/digest 和 `--artifact-metadata artifacts-api.json` 一并传给 validator。
10. 下载、解析或校验失败时保留 JSON `.part`、JSON、ZIP `.part`、ZIP、日志和解包证据，不自动删除、覆盖或复用。

保存响应 body 即可，不保存 Authorization header、token、完整请求环境或其他敏感认证材料。validator 不替代 Agent C 对账号、仓库、endpoint、latest run 和 attempt 的人工来源核对。

允许的本地操作仅限：读取文件、`apply_patch` 编辑、查看 diff/status、同步、暂存本轮文件、commit 和 push。Agent B 最终必须明确写出：未运行本地测试或检查，原因是人工要求全部测试/验收只走 GitHub Actions/CI。

Push 到 `origin/main` 后，由 `.github/workflows/ci-results.yml` 云端执行：

1. committed diff whitespace check、plist lint 和 workflow YAML parse。
2. `bash scripts/verify_project.sh`，覆盖 UI 展开合同、metadata 参数/结构/安全合同、成功与负向 fixtures、新旧兼容路径及所有既有验证。
3. `ChronoFocusMac` build。
4. `ChronoFocus` iOS generic build。
5. 上传既有未加密 CI 结果包；不得新增 API metadata 文件或其他上传内容。

## 9. 验收标准

### 9.1 UI

- 0 项显示既有通用或分类空态；1 至 4 项全部显示且没有展开控制。
- 5 项及以上默认只显示前 4 项，并准确显示“显示其余 N 项”。
- 展开后全部筛选结果可见并显示“收起”；收起后恢复前 4 项。
- 分类变化和 filtered count 变化均重置收起，N 始终来自当前筛选结果。
- 运行中展开/收起可操作，所有任务行仍不可切换；非运行状态任务选择保持原行为。
- 44pt、动态字体、VoiceOver label/value/hint 和 Voice Control 两态语义全部满足。
- iOS generic build 成功，新 UI marker/PASS 和 marker 缺失 fixture 通过。

### 9.2 CI metadata

- 三种允许参数组合按兼容矩阵工作，非法组合以清楚参数错误拒绝。
- metadata 必须满足非空、1 MiB 上限、普通文件和拒绝 symlink。
- 原始 API JSON 使用结构化解析，唯一 artifact 的所有指定字段均独立复判。
- API JSON、archive 参数与实际 ZIP 的 size/digest 三方一致。
- 八个 metadata PASS、三个 archive PASS、新 marker PASS 和所有既有 validator PASS 全部出现。
- 正负 fixture 精确命中目标检查，不以一个提前失败掩盖其他关键路径。
- workflow artifact 上传文件集合、名称、index 和 retention 未扩大。

### 9.3 Agent C 云端验收

- `origin/main` 最新 commit 与待验收 commit 完全一致。
- 最新 run 结论为 success，run attempt 已从 workflow run API 独立核对。
- Artifact API 原始 JSON、artifact id/name/size/digest/expired/workflow run 字段核对通过。
- JSON `.part`、JSON、ZIP `.part`、ZIP 和解包流程符合全新目录、无覆盖、原子改名和失败保留规则。
- Validator 使用 `--artifact-metadata` 和完整 archive 参数返回全 PASS。
- manifest、index、run context、JUnit、failure summary、主日志、Mac/iOS build、快照和项目专属 marker 全部通过。
- 完整 Actions 日志无未解释失败、弃用告警或 artifact 上传异常。

## 10. 风险与处理

- 展开状态若只在 chip 点击时重置，会漏掉摘要清除、空态清除和仓库更新；必须观察状态值和 filtered count，而不是特定按钮。
- 若把 `.disabled(engine.isRunning)` 放在包含展开按钮的父容器，运行中将无法展开；禁用范围必须只覆盖任务选择行。
- 数量变化时立即收起可能改变用户当前视图，但可避免展开状态跨越新增/完成后的不同结果集并产生错误剩余数；这是本轮明确行为。
- 动态字体可能让展开文案换行；应保持 44pt 最小高度并允许纵向增长，不截断内容。
- GitHub API 可能增加字段；只校验必要字段，不使用精确全键集合。
- 旧 artifact 可能没有 digest，但 v0.99 只验收当前 `upload-artifact@v6` 最新 run；缺失或 null digest 必须失败，不得降级。
- API response 文件不是加密签名；validator 只验证一致性，Agent C 仍负责账号、endpoint 和最新 run 来源。
- Artifacts API 不含 run attempt；必须保留名称、包内 runAttempt 和 workflow run API 三层关联，禁止虚构直接字段。
- 1 MiB 上限应在读取 JSON 前检查，避免对异常响应进行无界内存读取。

## 11. 禁止项

- 禁止本地测试、检查、构建或 fixture。
- 禁止跳过 Agent A -> Agent B -> Agent C 顺序。
- 禁止在 View 中创建第二套计时或分类持久化状态。
- 禁止运行中通过展开后的任务行切换当前任务。
- 禁止固定或伪造“其余 N 项”计数。
- 禁止 metadata 参数悄悄降级、接受部分 archive 参数、接受 symlink 或超限文件。
- 禁止用 grep、字符串切片、`eval` 或 shell 解析 JSON。
- 禁止把 API JSON、token、认证 header 或下载缓存上传到 artifact。
- 禁止修改 artifact 上传内容、下载历史 artifact 或复用旧缓存。
- 禁止删除失败证据、覆盖已有 `.part`/JSON/ZIP/解包目录。
- 禁止把旧 run、本地输出或包内自报字段冒充最新 API 外部证据。
- 禁止提交两份未跟踪用户文件或任何无关 diff。

## 12. Commit、Push 与 Agent C 闭环

Agent B 完成实现和文档后：

1. 只读核对实际 diff 和工作区归属，不运行任何检查。
2. 仅暂存 v0.99 相关文件。
3. 确认 `update_log.md` 已记录 v0.99，但在云端结果产生前不伪造 run/artifact 信息。
4. 使用固定提交信息：`v0.99: 展开iOS计时队列并复判Artifact API`。
5. 确认当前分支为 `main`、远端目标为 `origin/main`。
6. 直接 `git push origin main` 触发 GitHub Actions。
7. 记录真实 commit SHA、run id、run attempt、artifact id/name/API size/digest/expired 和 workflow run 身份。

Agent C 必须按第 6.11 节保存原始 API JSON 和 ZIP，使用 v0.99 完整 validator 调用验收最新 artifact。若任一云端步骤、fixture、build、metadata、archive、manifest 或 marker 失败，Agent C 判定不通过并列出证据；Agent B 在 `main` 追加修复 commit 后再次 push，禁止回滚或跳过失败。

若 Agent C 为补齐真实云端证据而修改 `update_log.md` 或其他验收文档，该记录提交本身也会成为新的 `origin/main` HEAD，必须再次等待其最新 run，并对该提交对应的新 API JSON、原始 ZIP 和 artifact 完成同样复判。只有最新 `origin/main` commit 的最终 run/artifact 全部通过后，v0.99 才能宣布闭环完成。
