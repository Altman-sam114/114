# v0.98 实现提示词：日程分类空态互斥与 CI 失败摘要直出

## 1. 版本号与分配依据

- 版本号：`v0.98`。
- 分配依据：最新 `origin/main` 已完成并验收 v0.97，`update_log.md` 与 `md/prompt/README.md` 的最新正式版本均为 v0.97；本轮在其后顺延一个小版本。
- 本轮性质：不改变核心数据模型、计时状态机或 artifact 格式的小步 UI/CI 可用性优化。
- 提交信息固定格式：`v0.98: 优化日程分类空态并直出CI摘要`。

## 2. 背景

### 2.1 iOS/macOS 日程分类空态重复

iOS `ScheduleView` 和 macOS `MacScheduleDetailView` 的待办列表都已经具备：

- 分类筛选条；
- 非空分类摘要，包含当前分类、新增此分类和清除筛选；
- 分类无结果空态，包含新增此分类和清除筛选。

当前两端都会在 `selectedCategory != nil` 时先渲染分类摘要，再在 `visibleTasks.isEmpty` 时渲染分类空态。因此分类筛选无结果时会同时出现两套新增/清除操作，也会产生重复的 VoiceOver 上下文。v0.97 的 iOS 计时页已经采用“非空显示摘要、空结果只显示空态”的互斥规则，本轮将相同交互原则收敛到 iOS/macOS 日程待办列表。

### 2.2 Final CI status 的失败摘要不可直接从步骤日志查看

`.github/workflows/ci-results.yml` 已生成 `ci-results/ci-failure-summary.md`，`Final CI status` 当前使用：

```bash
cat ci-results/ci-failure-summary.md >> "$GITHUB_STEP_SUMMARY"
```

这会把摘要写入 GitHub Step Summary，但不会同时写到该步骤 stdout。失败时，查看 Actions 步骤日志的 Agent/人工需要额外切换页面或下载 artifact 才能看到同一摘要。本轮要求使用 `tee` 将既有摘要同时输出到 stdout 和 `$GITHUB_STEP_SUMMARY`，但不能复制摘要文件、增加 artifact 条目、改变 manifest/index allowlist 或扩大结果包体积级别。

## 3. 本轮目标

### 目标 A：iOS/macOS 日程分类摘要与分类空态互斥

1. iOS `ScheduleView`：
   - 只有 `selectedCategory != nil` 且 `visibleTasks` 非空时显示 `SelectedCategorySummaryView`。
   - `visibleTasks` 为空且存在分类筛选时，只显示现有 `ScheduleCategoryEmptyStateView`。
   - 分类空态只保留现有“新增此分类”和“清除筛选”双操作，不新增第二套按钮、说明卡片或替代状态。
2. macOS `MacScheduleDetailView` 的 `MacTaskListPanelView`：
   - 只有 `selectedCategory != nil` 且 `visibleTasks` 非空时显示 `MacSelectedCategorySummaryView`。
   - `visibleTasks` 为空且存在分类筛选时，只显示现有 `MacScheduleCategoryEmptyStateView`。
   - `isSnapshotRendering` 下遵守同样互斥规则，继续复用现有空态静态操作，不新增快照专用业务分支。
3. 非空筛选态保持现状：摘要中的分类、计数、新增、清除和可访问语义都必须保留。
4. 空态保持现状：新增动作继续预填当前分类，清除动作继续恢复全部分类，VoiceOver 与 Voice Control 语义不退化。

### 目标 B：CI 失败摘要同时直出 stdout 与 Step Summary

1. `.github/workflows/ci-results.yml` 的 `Final CI status` 必须在 `if: always()` 下读取现有 `ci-results/ci-failure-summary.md`。
2. 使用 `tee` 一次完成两路输出，建议采用无多余 `cat` 进程的形式：

   ```bash
   tee -a "$GITHUB_STEP_SUMMARY" < ci-results/ci-failure-summary.md
   ```

3. `tee` 必须发生在最终 outcome 判断和 `exit 1` 之前，使成功和失败 run 都能在步骤 stdout 与 Step Summary 看到摘要。
4. 保留 `set -euo pipefail`、四个阶段 outcome 环境变量、原失败条件和退出语义。
5. 保持 `ci-failure-summary.md` 的生成内容、路径和 artifact 内唯一副本不变；不得在 `ci-results/` 中新增 stdout 副本或 summary 副本。
6. 保持 artifact 结构和体积级别不变：
   - 不新增、删除或改名 artifact 文件/目录；
   - 不修改 manifest、artifact index、project reports、required entries 或 allowlist；
   - 不修改 artifact 名称、上传路径、retention、`CI_PROCESS_VERSION` 或 upload 条件；
   - 不把完整摘要再次写入任何 artifact 日志文件；
   - 允许 `verify_project.log` 因新增一行契约 marker 产生必要的微小字节变化，但不得引入重复摘要或大段额外日志。

## 5. 当前架构依据

- iOS 日程 UI 位于 `ChronoFocus/Views/ScheduleView.swift`；`visibleTasks` 是当前日期范围与分类筛选后的唯一列表派生值。
- macOS 日程待办列表位于 `ChronoFocusMac/Views/MacScheduleDetailView.swift` 的 `MacTaskListPanelView`；`visibleTasks` 是当前未完成待办及分类筛选后的派生值。
- 两端分类状态只属于 View 展示筛选，不应写入 `FocusStore`；本轮不能新增持久化字段。
- iOS 新增分类待办继续通过 `showingEditor` 与 `TaskEditorView(initialCategory:)` 完成。
- macOS 新增分类待办继续通过现有 `onAddTaskInCategory`/快速新增请求完成。
- CI 结果包由 `.github/workflows/ci-results.yml` 生成；`Final CI status` 只负责展示摘要并根据前置阶段 outcome 设置 job 最终状态。
- `scripts/verify_project.sh` 负责源码/workflow 静态契约和负向 fixture；`scripts/validate_ci_artifact.rb` 负责 Agent C 对下载结果包的结构化复判。
- 现有 iOS/macOS 分类空态 marker 与 validator PASS 必须保留；本轮 CI 摘要直出需要新增独立 marker/PASS，不能借用无关 marker 自证。

6. 解包到全新目录，并调用：

   ```bash
   ruby scripts/validate_ci_artifact.rb <artifact-directory> \
     --commit <origin-main-sha> \
     --run-id <run_id> \
     --attempt <run_attempt> \
     --archive <artifact-name>.zip \
     --archive-size <api-size-in-bytes> \
     --archive-digest <api-sha256-digest>
   ```

7. 核对 manifest/run context/index 的 branch、完整 commit、run id、attempt、artifactName 与 API 一致；核对 JUnit、failure summary、static checks、`verify_project.log`、Mac/iOS build 日志、`.xcresult` 和 Mac 快照清单。
8. 除 artifact 内 `ci-failure-summary.md` 外，不得出现新增 summary 副本或未声明 entry；总 entry 清单与既有格式一致。
9. 查看 Actions `Final CI status` 完整步骤日志，确认 summary 内容确实出现在 stdout；同时核对 GitHub Step Summary。artifact 内 summary 只能证明文件内容，不能单独证明 `tee` 的两路 UI 输出，必须结合 workflow 静态契约和 run 页面证据。
10. 验收失败时保留 ZIP/`.part`/解包证据，不回滚；列出问题并退回 Agent B 在 `main` 追加修复 commit。

### 10.3 验收记录提交

若实现提交的云端验收通过后需要把真实 run/artifact 信息补入 `update_log.md`：

1. 在 `main` 追加文档提交并 push；
2. 该记录提交本身会触发新的 run；
3. Agent C 必须再次下载并验收记录提交对应的最新原始 ZIP；
4. 只有记录提交对应的最新 run/artifact 也通过，才能宣布 v0.98 完整闭环。

## 11. 风险

- 仅判断 `selectedCategory != nil` 而遗漏 `!visibleTasks.isEmpty`，会继续显示重复摘要。
- 把摘要条件绑定到总任务数而不是当前筛选后的 `visibleTasks`，会在日期范围或未完成过滤后产生错误状态。
- 删除摘要组件或按钮会破坏非空筛选态，而不是实现互斥。
- macOS snapshot 分支若另建状态判断，可能与真实 UI 分叉；应复用同一外层互斥条件。
- `tee` 放在失败判断后，会在 `exit 1` 时丢失失败摘要 stdout。
- 使用覆盖式 `tee "$GITHUB_STEP_SUMMARY"` 会覆盖其他步骤摘要；必须使用 `-a`。
- 使用错误重定向方向可能覆盖 `ci-failure-summary.md`；summary 文件只能作为输入。
- 只检查 workflow 全文包含 `tee` 而不限定 `Final CI status` 和顺序，会产生静态契约假阳性。
- 只新增 validator PASS 而没有 marker 缺失负向 fixture，无法证明结果包缺失证据会被拒绝。
- 为了证明 stdout 额外复制 summary 到 artifact，会违反结构/体积约束。
